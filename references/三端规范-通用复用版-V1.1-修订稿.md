# 三端规范 · 通用复用版

> **规范定位：** 桌面应用 Windows / macOS / Linux
> 跨平台工程治理规范，是《项目启动规范 ·
> 通用复用版》的平台专项补充，与《软件工程规范 ·
> 通用复用版》共同组成个人开发工程规范体系。
>
> **职责边界：** -
> 《项目启动规范》决定项目整体架构、分层、目录、文件职责与质量护栏。 -
> 《软件工程规范》决定开发过程中的代码质量、依赖、测试、重构与维护要求。 -
> 本规范决定桌面三端的平台抽象、平台差异、数据安全、构建发布与跨端验收。 -
> 项目专属规范负责记录具体技术选型、平台支持范围、目录落点和产品决策。
>
> **适用范围：** 以 Windows、macOS、Linux
> 为目标平台的桌面应用、桌面客户端及其配套服务。若项目只支持其中部分平台，应明确支持矩阵，不得将未支持平台表述为已支持。
>
> **采纳方式：**
> 新项目在正式业务开发前采纳；既有项目在跨平台改造、重大重构或二次开发前，先记录现状基线，再确定目标方案与迁移计划。项目采纳清单填写完成后生效。
>
> **规则等级：** MUST 为必须遵守；SHOULD
> 为原则上遵守，偏离时需记录理由。MUST
> 不得因进度或单端便利而被口头跳过；确需偏离时，按第 31
> 条登记、评估并批准，不得事后补票。
>
> **解释原则：**
> 本规范约束的是跨平台边界与结果，不要求三端内部实现完全相同。允许平台原生体验差异，但核心业务语义、数据含义和用户权益必须保持一致。

# 总则

## 1. 三端是同一产品的多个构建目标（MUST）

**要求**

项目必须明确各目标平台的支持范围、功能基线和兼容承诺。

核心业务能力、业务规则、数据格式和配置语义应保持一致。平台原生交互、系统集成方式、安装方式及受系统能力限制的功能可以存在差异，但必须在平台差异总表中登记；影响用户能力的差异还必须按第
29 条申报。

不得将某一端已实现、其他端未实现的功能笼统描述为「三端均支持」。

**为什么**

三端是同一产品的不同交付形态，而不是三个各自演进的产品。核心语义分叉会导致跨设备数据不一致、行为不可预测和维护成本上升。但强求界面与系统交互完全相同，又会破坏平台原生体验。

**怎么验**

-   任取一项核心功能，对照三端的输入、业务结果和持久化数据。
-   核对平台差异总表与实际功能状态。
-   未支持或降级的平台能力有明确标注。

## 2. MUST 条款不得因进度压力被跳过（MUST）

**要求**

MUST
条款在赶工、单端先行、临时修复和发布压力下仍然有效。不得以「先在一端跑起来」「以后再补」「这端比较特殊」作为跳过理由。

确有技术限制时，必须先识别影响、提出替代控制措施，并按第 31
条登记例外。安全、用户数据保护和发布真实性相关要求，不得通过普通例外降低底线。

**为什么**

跨平台问题经常在单端开发顺利时被忽略，直到其他平台或用户环境才暴露。规则必须能在压力场景下保持一致，同时也要允许经过评估的合理技术决策。

**怎么验**

抽查结构性变更和发布记录，确认 MUST
偏离均有事前评估、责任人、影响范围和复审条件；不存在仅以进度为理由的豁免。

# 第一部分：平台抽象与依赖边界

## 3. 唯一平台抽象边界，内部按职责拆分（MUST）

**要求**

全仓必须只有一个对业务层提供平台能力的抽象边界。平台判断、平台命令、平台默认路径及平台专属系统调用必须收敛在该边界及其明确授权的构建/打包配置中。

「唯一平台层」指唯一的架构边界，不代表只能有一个源文件或一个实现模块。平台层内部必须按职责拆分，例如：

-   操作系统与运行时信息。
-   路径与目录。
-   文件系统差异。
-   进程管理。
-   外部命令与脚本。
-   系统集成、权限与凭据。
-   各操作系统的具体适配实现。

业务层通过语义化接口表达意图，不直接调用平台专属命令或
API。允许平台层内部使用条件编译、平台命令和系统 API。

**为什么**

平台分支散落各处时，容易出现一端修复、另一端遗漏。把平台能力收敛到唯一边界，才能集中审计和测试；允许内部拆分，则可避免平台层自身成为新的巨型文件。

**怎么验**

-   全仓搜索平台条件编译、平台命令名和平台默认路径。
-   命中位置应仅位于平台抽象边界、平台实现和明确授权的构建/打包配置。
-   业务模块通过平台接口调用能力，不直接执行平台命令。

## 4. 随环境变化的值必须运行时推导（MUST）

**要求**

凡随操作系统、CPU
架构、当前进程、用户、机器、安装位置、运行环境或权限变化的值，必须从系统/框架
API 运行时推导，或由用户明确配置。

产品级固定常量可以静态定义，但必须集中管理并注明含义、单位、适用范围及来源。不得把开发机路径、用户名、机器架构、安装目录等环境值写死在业务代码中。

**为什么**

写死的值在开发机上可能始终正常，到用户机器上才失败，而且故障受环境影响，难以复现。

**怎么验**

在不同用户名、非默认安装位置和目标平台环境下走查主链路；搜索仓库中的绝对路径、用户名、平台字面量和机器环境假设。

## 5. 平台决策逻辑与环境探测分离（MUST）

**要求**

可独立表达的规则判断，例如 os/arch
映射、资源选择、兼容性判断和平台策略匹配，应设计为纯函数，将操作系统、进程架构、能力标记等作为显式输入。

真实环境探测（读取系统信息、查询权限、检查可执行文件、探测系统服务）允许在平台适配层执行，但探测结果应转换为明确的数据结构，再交由规则逻辑判断。

不得要求纯函数内部直接读取全局环境，也不得为了追求纯函数而伪造系统探测结果。

**为什么**

纯函数便于在单台机器上通过测试向量覆盖多平台决策；环境探测则必须尊重真实系统。二者分离，才能兼顾可测试性与真实性。

**怎么验**

-   存在覆盖目标平台输入的判定测试向量。
-   规则函数不直接读取全局环境。
-   环境探测集中在平台适配层，并对失败、未知和不支持状态有明确表达。

## 6. 外部生态命名口径分离映射（MUST）

**要求**

同一平台在不同外部生态、框架、打包工具或更新服务中的名称可能不同。每套外部口径必须单独映射，并以对应生态的官方定义为准。

禁止把某一生态中的平台名称直接复用到另一生态，或通过未经验证的字符串推导后写入配置、资产名和发布元数据。

**为什么**

平台名称混用可能不报错，却会静默选择错误资源，是隐蔽的跨平台故障来源。

**怎么验**

映射表按生态分别命名；测试向量覆盖每套映射；发布资产和更新元数据与对应生态的命名要求一致。

## 7. 平台默认值、用户配置与运行时派生值分离（MUST）

**要求**

必须区分三类数据：

1.  **平台默认值：** 由平台层根据系统规则推导，例如默认配置目录。
2.  **用户覆盖值：** 用户主动设置并持久化的值，例如自定义下载目录。
3.  **运行时派生值：**
    当前运行环境动态探测的值，例如进程架构、当前可用能力。

默认值只能由指定事实源产生。用户配置应保存用户实际选择，不得将平台默认值重复写入多个模块。运行时派生值不得冒充用户配置。

对于有默认值的用户配置，采用明确的解析规则：有效用户值优先；缺失或无效时采用平台默认值；默认值不可用时执行已登记的回退策略或给出明确错误。不得静默覆盖用户有效配置。

前端不得自行推导平台默认路径或复制平台规则；需要时通过后端/平台接口获取。

**为什么**

默认值、用户选择和运行时状态混为一谈，会造成配置覆盖、跨端迁移异常和多处默认值漂移。

**怎么验**

-   每类值都有唯一来源和明确类型。
-   修改平台默认值后，未设置用户覆盖值的场景同步变化。
-   用户自定义值在重启、升级和跨版本迁移后保持有效。
-   前端不存在重复的平台默认路径字面量。

# 第二部分：平台差异与系统语义

## 8. 平台差异总表是唯一权威清单（MUST）

**要求**

项目必须维护一份平台差异总表，记录已知差异及其代码落点。至少按项目适用情况覆盖：

-   外部平台命名与架构口径。
-   支持的 CPU 架构与运行时架构。
-   配置目录、数据目录、缓存目录。
-   可执行文件名与资源定位。
-   打开文件/链接、进程启动与结束方式。
-   脚本格式与执行权限。
-   路径分隔、大小写、符号链接及文件占用语义。
-   文件选择、拖放、剪贴板和系统通知。
-   渲染引擎及其运行时依赖。
-   窗口形态、托盘/菜单栏和系统集成。
-   权限、沙箱、凭据存储能力。
-   安装、更新、卸载和数据保留行为。
-   构建、签名、公证和发布资产。

差异总表描述「有什么差异、影响什么、由哪个模块处理」；项目目录地图描述「代码放在哪里」。两者互相引用，但不得互相替代。

新增平台差异先更新总表，再实施代码；发现实际行为与总表不符时，必须同步修正。

**为什么**

平台差异散落在代码、文档和个人经验中，会导致实现与交付口径不一致。统一清单使差异可发现、可审计、可维护。

**怎么验**

抽查平台条件分支和平台适配实现，每个差异都能在总表找到对应说明、代码落点和验证方式。

## 9. 路径必须使用路径语义处理（MUST）

**要求**

路径拼接、解析、比较和转换必须使用语言或框架提供的路径类型/API，不得通过字符串拼接分隔符构造路径，不得将预拼接路径字符串作为跨平台内部数据模型。

配置目录、数据目录和缓存目录优先使用框架或操作系统提供的应用目录
API。目录无法获取时，必须在平台层定义有序回退策略；回退失败应返回可诊断错误，不得悄悄退到当前工作目录。

路径进入文件操作前，应根据操作场景进行规范化与安全校验。处理用户输入、压缩包和导入内容时，必须防范路径穿越、绝对路径逃逸和符号链接绕过。不得仅依赖字符串前缀判断路径是否位于目标目录内。

**为什么**

字符串拼路径会在空格、中文、不同分隔符和挂载点场景下失效。路径安全检查不充分，还可能导致覆盖或读取目标目录之外的文件。

**怎么验**

-   在含中文、空格、非默认盘符/挂载点的路径下测试。
-   测试相对路径、绝对路径、符号链接和路径穿越样本。
-   检查路径拼接是否使用路径 API。
-   检查目录 API 失败时的回退行为。

## 10. 公共文件操作按最严格的目标语义设计（MUST）

**要求**

公共逻辑不得依赖某一平台较宽松的文件系统行为。

至少遵守：

-   文件名与路径比较不得假设大小写不敏感；按大小写敏感场景设计。
-   替换、移动或删除文件时，必须考虑文件可能被占用或锁定。
-   处理文件名冲突时，明确大小写折叠、Unicode 规范化和冲突策略。
-   解压、导入和同步操作必须防止路径穿越与符号链接逃逸。
-   对权限不足、只读文件系统、磁盘空间不足和跨卷移动失败给出可诊断结果。

需要注意：不同文件系统的大小写和 Unicode
规则可能不同。按最严格语义设计是为了避免错误假设，不代表可以绕过目标文件系统的真实行为。

**为什么**

大小写、文件占用、权限和符号链接问题，常在开发机上不明显，却可能在用户数据操作时造成覆盖、丢失或失败。

**怎么验**

覆盖大小写不同的同名文件、文件占用、只读目录、跨卷移动、路径穿越和符号链接样本；目标平台均有对应验证记录。

## 11. 进程管理语义由平台层封装（MUST）

**要求**

进程启动、存活探测、结束、进程树/进程组处理、信号发送和提权执行等平台差异必须由平台层封装。

调用方表达语义意图，例如启动程序、请求终止、等待退出、检查状态，不直接依赖
taskkill、kill 等平台命令。

必须区分正常退出、超时、被信号终止、权限不足和目标进程不存在等状态。结束进程树时应明确范围，避免误杀无关进程。

**为什么**

不同系统的进程树、进程组和终止语义并不完全等价。调用方直接拼接平台命令，容易产生僵尸进程或误杀。

**怎么验**

启动包含子进程的目标程序后，验证正常结束、强制结束和超时处理；确认无非预期残留进程，也不影响无关进程。

## 12. 外部命令与脚本按平台安全生成（MUST）

**要求**

打开文件夹/链接、调用外部程序和生成脚本等操作必须由平台层实现。

-   优先使用进程 API 的参数数组，不得通过字符串拼接命令。
-   必须正确处理含空格、中文、特殊字符的参数。
-   确实需要 shell 时，必须明确 shell 类型、转义规则和输入可信边界。
-   生成 `.bat`、`.sh` 等脚本时，按目标平台生成正确内容。
-   类 Unix 脚本必须设置并验证可执行权限。
-   不得将用户输入直接拼入 shell 命令。

**为什么**

命令字符串拼接会引入路径解析错误和命令注入风险；脚本权限缺失则可能在用户端表现为点击无响应。

**怎么验**

在含空格、中文和特殊字符的路径下执行；使用恶意分隔符和 shell
元字符作为输入进行安全测试；生成脚本后立即验证权限和执行结果。

## 13. 渲染引擎与窗口形态按端登记（SHOULD）

**要求**

登记各端渲染引擎来源（系统自带、随包或系统依赖）、版本约束、缺失时提示方案，以及窗口形态（边框、标题栏、自绘、阴影、托盘/菜单栏等）。

应用启动时应避免向用户展示长时间无反馈的空白窗口。可以采用界面就绪后显示、启动占位页或等价机制；启动失败必须有可见、可诊断的反馈。

**为什么**

渲染引擎和窗口系统差异会影响启动、界面一致性和系统集成。用户看到白屏时无法判断应用是在加载还是已经失败。

**怎么验**

各端冷启动检查首屏；模拟运行时依赖缺失和初始化失败，确认用户得到明确提示，而不是永久白屏。

# 第三部分：分端要求

## 14. Windows 要点（MUST）

**要求**

-   对 WebView2 等运行时依赖进行检测，并提供可达的安装指引和失败说明。
-   明确用户级、系统级安装形态的安装目录、配置目录、升级覆盖和卸载行为。
-   验证长路径、含空格和中文的路径；若目标环境或打包方式不支持某些长路径场景，必须明确限制。
-   处理文件占用、权限不足、UAC 和进程结束差异。
-   安装、升级和卸载不得静默删除用户数据。

**为什么**

Windows
用户环境差异较大，运行时缺失、安装权限、安装范围和特殊路径都可能影响启动与升级。

**怎么验**

在干净虚拟机中测试运行时存在/缺失、无网络、用户级/系统级安装、长路径、升级和卸载流程。

## 15. macOS 要点（MUST）

**要求**

-   发布架构方案必须明确：Universal、分别构建或其他受支持方式；不得仅凭机器型号猜测运行时架构。
-   涉及原生库和资源选择时，以当前进程实际架构为准。
-   所有路径通过系统/框架 API 推导，不依赖启动工作目录。
-   遵守系统隐私权限、沙箱和文件访问授权机制；授权失败时给出明确说明和可执行的恢复指引。
-   默认数据目录不得随意落入系统受保护目录。
-   明确支持的启动方式；若不支持从 dmg
    等分发介质直接运行，必须在安装或启动时给出说明。
-   签名与公证状态必须与实际发布包一致。

**为什么**

macOS
的转译运行、启动工作目录、隐私授权、沙箱和签名公证会显著影响应用行为。

**怎么验**

在支持的架构环境下测试；分别从 Finder
和终端启动；验证文件授权、受保护目录、签名、公证和安装后启动流程。

## 16. Linux 要点（MUST）

**要求**

-   明确构建基线及其兼容承诺，包括 glibc
    和关键系统库要求；发布说明必须写明基线。
-   各包型分别声明依赖：系统包通过包元数据声明；独立包明确运行前提及缺失依赖时的处理方式。
-   发行版名称和包管理器命令只允许出现在安装、打包或明确授权的系统集成层；业务代码不得根据发行版拼接安装命令。
-   明确支持的显示服务、桌面环境和系统集成能力；涉及 X11、Wayland
    的功能应列入差异表。
-   对缺少桌面凭据服务、文件选择器或其他可选系统服务的环境，定义能力探测和降级策略。

**为什么**

Linux
发行版、桌面环境、依赖版本和包管理方式存在差异。通过明确基线、依赖声明和能力探测控制差异，比在业务代码中猜测发行版更可靠。

**怎么验**

在基线发行版和至少一个较新目标环境安装运行；检查依赖缺失提示；按项目支持范围验证
X11/Wayland、拖放、剪贴板和文件选择等功能。

## 17. 架构口径以当前进程为准（MUST）

**要求**

凡涉及原生库、运行时、动态库和资源选择的架构判断，必须以当前进程实际架构为准。不得使用机器型号、系统信息页或安装包目标架构代替进程架构。

构建目标架构、安装包架构和运行时进程架构是不同概念，必须分别命名、分别记录。

**为什么**

转译、兼容层和通用二进制会使机器架构与进程架构不一致。按机器型号猜测可能导致加载错误的原生资源。

**怎么验**

在存在转译或兼容运行的场景中启动应用，核对运行时选择的原生资源与当前进程架构一致。

# 第四部分：数据、配置与凭据

## 18. 配置位置统一且向后兼容（MUST）

**要求**

配置文件位置由平台层统一推导；三端尽量使用一致的文件名、字段语义和
schema。平台路径可以不同，但配置含义不得因平台而改变。

配置 schema 变更必须提供迁移策略：

-   新版本能够读取受支持的旧版本配置。
-   迁移前保护原始配置。
-   迁移成功后再提交新配置。
-   迁移失败时保留原始数据，并提供恢复或诊断信息。
-   不支持的未来版本配置不得被静默覆盖。

**为什么**

配置属于用户数据。只要求新版读取旧版还不够，还必须防止迁移中断造成配置损坏。

**怎么验**

使用上一个受支持版本的真实配置启动新版；覆盖迁移成功、迁移中断、字段缺失、未知字段和未来
schema 版本场景。

## 19. 凭据使用安全存储，降级必须受控（MUST）

**要求**

访问令牌、刷新令牌、密码、API 密钥等敏感凭据禁止存入前端
localStorage、sessionStorage、普通日志或明文配置文件。

优先使用操作系统提供的安全凭据存储：

-   Windows Credential Manager。
-   macOS Keychain。
-   Linux Secret Service 或项目明确支持的等效安全服务。

如果目标环境没有可用的安全凭据服务，必须明确威胁模型、降级方案、加密与密钥管理方式、文件权限和用户告知方式。不得将明文配置文件作为默认回退。

凭据存储接口由统一安全/平台边界提供，业务模块不得各自实现存储方案。三端能力和降级状态必须记录在差异总表中。

**为什么**

凭据泄露会造成账户和数据风险。不同平台安全存储能力不同，但不能因为某端实现困难就默认降低安全等级。

**怎么验**

-   检查前端存储、日志和普通配置中不存在敏感凭据。
-   验证三端凭据实际落点、访问权限和删除行为。
-   在无可用凭据服务的环境验证受控降级。
-   检查异常日志不输出凭据内容。

## 20. 用户数据处置默认不删除（MUST）

**要求**

更新、修复、回滚和卸载流程默认保留用户配置、数据目录、存档和用户主动导入的内容。

任何删除或覆盖操作必须满足：

1.  明确告知用户操作对象和影响范围。
2.  提供可恢复机制，或明确说明不可恢复并取得用户确认。
3.  不得将应用缓存、临时文件与用户数据混为一谈。
4.  不得在失败或异常退出时静默清理用户数据。

**为什么**

误删用户数据可能造成不可逆损失。不同平台安装器和卸载器的默认行为不同，必须由产品主动统一。

**怎么验**

三端分别执行升级、修复、回滚和卸载，核对数据保留策略；对删除操作验证确认提示和恢复机制。

## 21. 文件写入与替换必须具备故障保护（MUST）

**要求**

对配置、索引、数据库快照、用户存档等重要文件进行覆盖式更新时，必须设计故障保护流程。

在文件系统和业务条件允许时，采用临时文件写入、刷新/同步、校验、原子替换的方式提交。跨卷移动、网络文件系统或不具备原子替换语义的场景，必须使用适当的备份与恢复策略，不得假定所有平台都提供相同保证。

必须处理磁盘空间不足、权限不足、文件占用、进程中断和替换失败等情况。

**为什么**

程序崩溃或断电可能发生在写入过程中的任意时刻。直接覆盖重要文件可能造成数据截断或损坏。

**怎么验**

在写入、刷新、替换等关键阶段模拟失败或中断；确认旧数据仍可恢复，且不会把不完整文件当作成功结果。

## 22. 数据迁移必须可验证、可恢复（MUST）

**要求**

涉及用户数据结构、数据库
schema、索引格式或存储布局的升级，必须有明确迁移版本和迁移路径。

-   迁移前确认备份或可恢复条件。
-   迁移步骤应可诊断，必要时采用事务或分阶段提交。
-   明确迁移成功的判定条件。
-   失败时保留原始数据，并提供重试或恢复路径。
-   不得在未验证新数据可用前删除旧数据。
-   不支持的降级回滚必须提前说明，不能假装可逆。

**为什么**

配置兼容只是数据兼容的一部分。数据库和用户存档迁移失败，可能比应用启动失败造成更严重的损失。

**怎么验**

使用真实旧版本数据执行升级；覆盖迁移成功、重复执行、迁移中断、回滚和数据校验场景。

# 第五部分：系统能力与生命周期

## 23. 按能力探测，不仅按操作系统分支（MUST）

**要求**

当功能取决于桌面环境、系统服务、权限、显示协议或可选依赖时，应优先探测实际能力，而不是仅根据操作系统名称推断。

能力状态至少区分：

-   可用。
-   不可用。
-   未知或探测失败。
-   用户未授权。
-   暂时不可用。

平台层将探测结果转换为统一能力描述；业务层根据能力决定启用、降级或提示。不得把探测失败误判为能力不存在，也不得把未知状态当作可用。

**为什么**

同一操作系统的不同版本、发行版、桌面环境和权限设置可能提供不同能力。仅按
Windows/macOS/Linux 分支不足以判断真实运行条件。

**怎么验**

构造能力存在、缺失、权限拒绝和探测异常场景；确认功能状态和提示与实际能力一致。

## 24. 权限与沙箱行为必须显式处理（MUST）

**要求**

访问文件、麦克风、摄像头、辅助功能、网络、本地服务或其他受保护资源时，必须遵守操作系统权限和沙箱机制。

-   不得假设应用始终拥有管理员或完全文件访问权限。
-   需要授权时，在合适时机向用户解释用途。
-   授权拒绝、撤销或过期时，返回明确状态。
-   不得通过绕过系统安全机制来实现功能。
-   需要提权的操作必须限定范围、明确告知并最小化执行时间。
-   权限相关平台差异登记在差异总表。

**为什么**

开发环境通常拥有比普通用户更高的权限。权限假设会造成应用在用户机器上失败，也可能引入不必要的安全风险。

**怎么验**

使用普通用户、拒绝授权、撤销授权和受限目录进行测试；确认失败可解释、可恢复，且没有隐式提权。

## 25. 单实例、锁与实例通信必须定义语义（SHOULD）

**要求**

如果产品要求单实例运行，必须明确单实例范围、锁的生命周期、异常退出后的恢复方式，以及第二次启动时的行为。

跨进程通信应验证发送方、消息内容和目标实例状态；不得仅依赖可能残留的锁文件判断进程仍然存活。

若产品允许多实例，必须明确配置、缓存、数据库和用户数据的并发访问策略。

**为什么**

不同平台的文件锁、进程检测和实例通信方式不同。未定义语义容易产生重复进程、锁死或数据竞争。

**怎么验**

覆盖重复启动、异常退出、锁残留、并发访问和实例通信失败场景。

## 26. 系统集成能力按端登记（SHOULD）

**要求**

文件关联、URL
Scheme、开机启动、系统托盘/菜单栏、通知、拖放、剪贴板、默认浏览器和系统代理等能力，应明确：

-   是否支持。
-   由哪个模块实现。
-   需要什么权限或系统条件。
-   安装、升级和卸载时如何注册与清理。
-   不可用时如何降级。

不得在业务模块中散落系统注册表、桌面文件、LaunchAgent
或其他平台专属配置操作。

**为什么**

系统集成是桌面应用体验的重要部分，也最容易因平台差异形成隐性依赖。

**怎么验**

按项目支持范围逐项检查注册、使用、升级覆盖和卸载清理；差异总表与实际行为一致。

# 第六部分：打包与发版

## 27. 发版资产契约必须保持一致（MUST）

**要求**

每个版本的发布资产清单是对外契约，至少明确包型、文件名模板、目标平台、CPU
架构和校验信息。

凡官网、自动更新、下载脚本或文档按规则匹配的资产，发生改名、增减包型或命名模板变化时，必须先同步修改全部下游匹配规则，并在发版前后验证。

**为什么**

资产名可能被多个外部入口依赖。只改构建产物而不改下载和更新规则，会导致用户无法获取正确版本。

**怎么验**

发版前检查资产清单与下游规则；发版后逐项验证下载链接和更新检查实际指向本次版本。

## 28. 版本号必须有唯一事实源（MUST）

**要求**

版本号必须指定唯一事实源，例如打包配置或统一版本文件。应用展示版本、安装包元数据、发布标签、更新清单和发布说明必须由该事实源生成或校验。

禁止多处手工维护同一版本号。发布说明和变更日志必须能追溯到实际提交、变更记录和发布时间，不得编造。

**为什么**

版本字段多处维护容易漂移；发布说明与实际提交不一致会损害用户信任，也增加故障定位难度。

**怎么验**

发版脚本核对各版本字段一致；抽查变更日志条目与提交记录对应。

## 29. 单端降级与未支持能力必须显式申报（MUST）

**要求**

任何一端缺失、降级或暂不支持某项功能时，必须在交付/发版说明中点名：

-   平台。
-   功能。
-   当前状态。
-   原因或限制。
-   对用户的影响。
-   计划处理方式（如有）。

产品内应隐藏、禁用或提供明确提示，不得让用户进入必然失败的操作路径。不得用其他平台的成功结果代替该平台的验证结论。

**为什么**

静默缺失会让用户在使用中途才发现功能不可用，也会让开发者误判三端完成度。

**怎么验**

发版说明包含降级清单；无降级时明确写「无」；产品内入口状态与说明一致。

## 30. 签名、公证与安全提示必须如实（MUST）

**要求**

三端签名和分发要求分别明确：

-   Windows：代码签名状态及验证方式。
-   macOS：代码签名、公证与 Gatekeeper 相关状态。
-   Linux：根据分发方式确定仓库签名、包签名或校验和策略。

未签名、未公证或验证不完整时，官网、发布说明和安装提示必须如实标注，并提供正规、符合平台安全机制的处理指引。禁止教用户关闭或绕过系统安全机制来规避正常校验。

证书、私钥和口令只能通过受控密钥管理和 CI 注入，禁止入仓或写入构建日志。

**为什么**

签名状态直接影响用户能否安全识别发布者和验证产物。隐瞒状态或诱导用户绕过安全机制，会把风险转嫁给用户。

**怎么验**

逐个验证发布包签名、公证或校验状态；核对文档描述；检查仓库、构建日志和产物中不存在私钥与口令。

## 31. 构建矩阵与发布门禁不可静默缩水（MUST）

**要求**

项目必须明确三端构建矩阵、触发时机和发布门禁。

正式发布时，所有声明为本版本支持的目标平台与资产都必须完成规定构建和检查。任一必需构建失败、资产缺失或校验失败，整版不得发布。

如果项目明确采用分批发布或部分平台延迟发布，必须将版本状态、平台范围和用户影响写清楚，不得把部分平台构建结果描述为完整三端版本。

发布核对必须逐个确认资产存在、大小合理、校验信息正确，并能被下游入口获取。

**为什么**

「告警但放行」是缺包版本上线的常见通道。构建成功不等于所有用户都能下载到正确资产。

**怎么验**

发布清单逐项记录平台、架构、包型、构建状态和资产校验；人为移除一个必需产物时，流水线或发布检查能够阻止发布。

## 32. 下游联动必须进入发版清单（SHOULD）

**要求**

官网、更新通道、文档、下载页和脚本中引用版本或资产的地方，必须明确属于自动读取还是手工同步。

-   自动读取：记录缓存窗口、超时和回退策略。
-   手工同步：列入发版清单逐项确认。
-   发布后：验证用户入口确实指向本次版本。
-   更新失败：提供可诊断状态，不得静默显示更新成功。

**为什么**

发版不是构建成功就结束。下游入口未同步，用户仍然无法获得新版本。

**怎么验**

按发版清单逐项实测下载和更新入口；超时或未更新时执行既定处置流程。

# 第七部分：测试与验收

## 33. 跨端决策逻辑应可在单端覆盖（MUST）

**要求**

符合第 5
条条件的纯函数规则，应通过测试向量覆盖所有目标平台的输入组合。日常 CI
可以在单一平台运行这些测试，但报告必须明确这代表「跨端规则逻辑覆盖」，不代表已在所有目标系统完成真实运行验证。

涉及真实系统
API、权限、文件系统、进程、窗口、渲染和打包行为的内容，不能仅靠纯函数测试替代。

**为什么**

单端 CI
可以降低跨端逻辑验证成本，但不能证明真实系统行为一致。必须明确测试结论的边界。

**怎么验**

测试报告区分规则逻辑覆盖、平台集成测试、真实环境冒烟和发布资产验证；规则变化时同步更新测试向量。

## 34. 编译矩阵与触发口径必须明确（SHOULD）

**要求**

项目必须选择三端构建矩阵的触发方式，例如：

-   每次推送或合并请求。
-   主分支变更。
-   定期构建。
-   仅发布候选版本或发布标签。

若日常推送不触发全平台构建，必须明确记录覆盖缺口和风险，并确保发布门禁仍覆盖全部声明支持的平台。

**为什么**

跨端构建成本真实存在，可以根据个人项目资源选择触发频率，但不能把未执行的构建描述成已验证。

**怎么验**

CI 配置与项目记录一致；发布候选版本使用当前提交执行完整目标矩阵。

## 35. 平台集成测试与真实环境冒烟分级（MUST）

**要求**

测试证据必须区分以下级别：

1.  纯函数/单元测试。
2.  平台 API 集成测试。
3.  虚拟机或等效真实系统环境测试。
4.  真实设备/真实用户环境冒烟。

正式发布前，所有声明支持的平台必须完成项目采纳清单规定的最低验证级别。涉及真实硬件、系统权限、窗口管理、签名、公证或系统集成的关键功能，应在真实目标环境验证。

个人开发或设备资源受限时，可以使用虚拟机、远程构建机或可信测试环境完成部分验证，但必须如实标注验证方式；未验证的平台不得标记为已通过。

每条验证记录至少包含平台版本、环境类型、测试日期、测试范围、结果和可追溯证据。

**为什么**

模拟测试和 CI
无法覆盖所有真实系统行为。分级验证既能适应个人开发资源，也能避免把逻辑测试误报为真机验证。

**怎么验**

发布记录逐平台列出验证级别和结果；未验证项明确列出，不得以其他平台通过代替。

## 36. 平台差异变更必须有针对性测试（MUST）

**要求**

新增或修改平台适配逻辑时，必须同步增加或更新对应测试。测试范围至少覆盖：

-   目标平台正常路径。
-   不支持或能力缺失路径。
-   权限拒绝或系统 API 失败路径。
-   路径含空格、中文或特殊字符的情况（适用时）。
-   资源缺失、进程异常或文件占用等边界（适用时）。

不得仅因某一端当前无法运行，就跳过可通过测试向量、模拟接口或其他受控环境验证的逻辑。

**为什么**

平台适配层集中承载差异，任何改动都可能影响特定系统。针对性测试能降低回归风险。

**怎么验**

代码变更与测试变更相互对应；测试报告能指出覆盖了哪些平台行为和失败场景。

# 第八部分：变更、例外与 AI Agent 执行

## 37. 平台架构与差异表变更必须留痕（MUST）

**要求**

以下变更必须更新平台差异总表及相关架构记录：

-   新增或删除支持平台。
-   修改平台抽象边界。
-   修改运行时架构或资源选择策略。
-   修改配置、数据或凭据落点。
-   修改平台能力支持范围。
-   修改构建、签名、包型和发布资产契约。
-   修改兼容基线或最低系统版本。

变更记录说明原状、目标、影响模块、迁移方案和验证方式。普通平台实现修复若未改变约定语义，可只更新差异表对应条目和测试记录，无需形成大型架构文档。

**为什么**

平台行为和代码结构会持续演进。文档不随变更更新，就会逐渐失去作为事实依据的价值。

**怎么验**

抽查平台相关提交，确认差异表、架构记录和测试证据与代码一致。

## 38. 例外必须逐项登记并设置复审条件（MUST）

**要求**

确需偏离 MUST 或 SHOULD 条款时，必须逐项登记：

  项目            内容
  --------------- --------------------------------
  规则编号        偏离的条款
  涉及平台/模块   具体对象
  原因            技术限制或产品决策
  风险与影响      对安全、数据、功能和维护的影响
  替代控制        如何降低风险
  批准记录        决策人及日期
  复审条件        何时重新评估

例外必须限定平台、模块和时间/版本范围，不得使用「项目特殊」作为全局豁免。

涉及凭据明文、用户数据静默删除、发布状态虚假描述或绕过系统安全机制的例外不得批准。

**为什么**

合理例外不可避免，但没有边界的例外会使规范失去约束力。登记和复审能使技术债务可见、可追踪。

**怎么验**

所有偏离项均能在例外清单中找到；清单外偏离视为未授权；到达复审条件时有处理结论。

## 39. AI Agent 必须遵守平台边界（MUST）

**要求**

参与项目开发的 AI
Agent、编码助手和自动化程序必须遵守本规范、项目采纳清单、平台差异总表及项目架构决策。

新增或修改代码前必须：

1.  阅读相关平台层接口和差异表。
2.  判断需求是否涉及平台差异、系统能力或平台专属资源。
3.  优先复用已有平台抽象，不得在业务层新增平台判断。
4.  检查是否影响其他目标平台。
5.  明确新增能力的降级、权限和失败处理。

涉及平台边界变更时，必须先说明变更理由、影响范围、目标接口和测试方案；不得擅自扩大支持范围或改变发布契约。

任务完成后必须检查：

-   平台判断是否外泄。
-   是否引入硬编码路径、命令或架构假设。
-   是否重复实现平台能力。
-   是否破坏配置兼容或用户数据安全。
-   是否同步更新差异表和测试。
-   是否真实执行了对应构建与验证命令。

AI Agent
不得把未执行的测试描述为通过，不得把模拟结果描述为真实平台验证。

**为什么**

AI Agent
生成和修改代码速度快，但容易在局部任务中忽略其他平台、既有接口和用户数据约束。明确执行边界可以减少跨端回归和结构漂移。

**怎么验**

抽查 AI Agent
的提交、变更说明和测试报告，确认平台边界、差异表、质量护栏和验证结论一致。

# 自查命令参考

以下命令仅为搜索起点，应根据项目语言、目录和框架调整；搜索命中不自动等于违规，必须结合实际代码判断。

``` bash
# Rust 平台条件编译：检查是否泄漏到平台抽象边界之外
grep -rn 'cfg(target_os\|cfg!(windows)' src crates --include='*.rs'

# 常见平台命令：检查业务层是否直接调用
grep -rn 'explorer\|xdg-open\|taskkill\|open -a' src crates

# 前端凭据存储：检查敏感字段是否进入浏览器存储
grep -rn 'access_token\|refresh_token' src \
  --include='*.ts' --include='*.tsx' --include='*.js' --include='*.vue'

# 硬编码绝对路径：按项目语言和目录进一步筛选
grep -rnE '(/Users/|/home/|[A-Za-z]:\\\\Users\\\\)' src

# 检查常见 shell 字符串拼接风险，命中后人工审查
grep -rnE 'sh -c|cmd /c|powershell.*-Command' src
```
