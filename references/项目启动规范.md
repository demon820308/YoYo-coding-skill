# 项目启动规范 · 通用复用版

> **规范定位：** 项目开工前的架构与工程骨架定版规范，与《软件工程规范 · 通用复用版》《三端规范 · 通用复用版》组成同一套工程规范体系。
>
> 《项目启动规范》管开工前的结构决策：项目采用什么架构、如何分层、代码放在哪里、文件如何组织、质量护栏如何建立。
>
> 《软件工程规范》管开发过程中的工程质量与代码治理。
>
> 《三端规范》管多端项目的端侧边界、通信协议与跨端协作。
>
> **核心主张：** 文件职责混杂、模块边界模糊、目录结构失控，往往不是开发者缺乏自觉，而是项目开始时没有建立明确的结构约束。本规范将职责拆分、文件落点和质量护栏前置到项目启动阶段，让每一份新代码在诞生时就有明确归属，而不是等问题积累后再集中重构。
>
> **适用范围：**
> - 新建项目：在第一批业务代码编写前完成骨架定版。
> - 既有项目：在重大重构、架构调整或二次开发启动前，先建立现状基线，再确定目标骨架与迁移方案。
> - 个人开发：以单人可维护、可验证、可持续演进为原则，不引入不必要的大型团队治理机制。
>
> **采纳方式：** 立项时引入本规范，根据项目实际情况填写文末《项目采纳清单》。必须项未完成，不得进入正式业务开发阶段；建议项根据项目实际情况采纳。
>
> **规则等级：**
> - MUST：必须遵守，偏离时必须明确登记理由。
> - SHOULD：原则上遵守，有合理原因时允许调整。
>
> 每条规范均包含「要求」「为什么」「怎么验」，确保规则不仅能阅读，还能被开发者和 AI Agent 实际执行。

---

# 总则

## 1. 骨架先行，定版留痕（MUST）

**要求**

在第一批业务代码编写之前，必须确定项目的基础工程骨架，并将决策结果写入仓库。

至少包括：

1. 项目采用的整体架构。
2. 系统分层与依赖方向。
3. 业务域与模块边界。
4. 目录结构及文件落点规则。
5. 文件职责与增长控制策略。
6. 测试、构建与质量验收方式。
7. 全局事实源及核心基础设施归属。

定版结果记录在项目规范文件中，作为后续开发、重构和 AI Agent 执行的共同依据。

允许先建立空目录、空模块、接口定义和最小化脚手架，但不允许在结构尚未明确时持续堆积业务实现。

对于既有项目，不要求追溯性地补造历史记录。应在新一轮重构或开发开始前完成现状评估、目标骨架定版和迁移计划。

**为什么**

架构和目录结构属于项目的基础性决策，越晚调整，涉及的代码、依赖、测试和调用关系越多。

Pure-Build 项目的 platform.rs 长期承载多类职责，最终增长到 692 行，说明问题不仅是文件太长，更是最初没有建立层内职责拆分和文件落点规则。

**怎么验**

- 仓库存在已填写的项目采纳清单。
- 新项目的定版记录早于第一批业务实现。
- 既有项目有明确的现状基线、目标结构和迁移计划。
- 后续开发能够依据清单判断新代码的归属。

## 2. 参数按项目实际情况确定，不照搬其他项目（MUST）

**要求**

本规范提供工程原则、决策方法和最低约束，不提供适用于所有项目的固定架构参数。

以下内容必须根据本项目确定：

- 分层数量与层级名称。
- 业务域划分。
- 目录结构。
- 文件行数参考阈值。
- 测试策略与覆盖范围。
- 构建和质量检查方式。

参数确定时，优先参考：

1. 当前技术栈与框架约束。
2. 项目现有脚手架和生成结构。
3. 同类模块的实际代码分布。
4. 项目的复杂度、规模和预期演进方向。
5. 已有工程工具能够提供的检测能力。

新项目没有历史数据时，可以采用本规范提供的初始参考值，待第一个完整版本形成后，根据实际情况校准。

**为什么**

脱离项目实际情况谈统一数字，容易导致规则失效。

例如，500 行对于平均 150 行的业务文件可能已经严重超长，但对于某些生成代码或协议定义文件，500 行可能完全正常。

**怎么验**

采纳清单中的每个关键参数都有确定依据。

无法解释参数来源、适用对象和调整理由的，不得直接作为强制标准。

# 第一部分：架构骨架

## 3. 分层与依赖方向先确定（MUST）

**要求**

项目开工前必须明确：

1. 整体采用什么架构。
2. 分为哪些层。
3. 每一层负责什么。
4. 每一层允许依赖哪些层。
5. 哪些依赖方向明确禁止。

原则上采用由外向内的依赖方向：

- 外层可以调用内层。
- 内层不应依赖外层的具体实现。
- 核心业务不直接绑定 UI 框架、操作系统或具体基础设施。
- 跨层通信通过明确的接口、类型或协议完成。

具体分层应根据项目规模确定，不强制所有项目采用相同层数。

增加一层时，必须说明该层隔离了什么职责或变化。

**为什么**

分层是项目的结构边界。

如果依赖方向没有提前确定，开发过程中很容易出现业务逻辑依赖界面、核心模块直接操作平台 API、底层模块反向调用上层实现等问题。

**怎么验**

采纳清单必须包含：

| 层级 | 核心职责 | 允许依赖 | 禁止依赖 |
|---|---|---|---|
| 按项目实际填写 | 一句话说明 | 明确列出 | 明确列出 |

随机抽查模块之间的 import、调用和依赖关系，确认符合分层约定。

## 4. 建立项目的「职责边界地图」（MUST）

**要求**

项目开工前必须识别代码未来会沿哪些职责边界进行组织，并形成明确的文件落点规则。

本规范将职责边界分为四个层次：

1. **架构层：** 代码属于哪个系统层。
2. **业务域：** 代码属于哪个业务领域。
3. **职责模块：** 代码承担什么具体职责。
4. **文件：** 具体实现、类型、接口或资源的存放位置。

常见项目的划分参考：

**A. 分层应用（桌面端、服务端、全栈应用）**

- 先按架构层划分。
- 层内按业务域划分。
- 业务域内按职责划分。
- 平台相关操作与通用业务逻辑分离。

**B. 静态站点、内容站、生成式站点**

- 内容数据与展示模板分离。
- 页面组件与构建脚本分离。
- 内容模型与具体页面实现分离。
- 构建产物、缓存和临时文件不作为业务源码管理。

**C. 库、SDK、CLI**

- 公开 API 与内部实现分离。
- 命令入口与命令执行逻辑分离。
- 内部实现按业务域或功能模块组织。
- 对外接口与具体平台实现分离。

**D. 前端与 UI 项目**

- 基础组件、业务组件、页面视图分离。
- 状态管理与视图展示分离。
- 样式 Token 与组件样式分离。
- 页面编排不承担复杂业务规则。

以上是组织思路，不是要求每个项目全部采用。

每一段新代码开始编写前，都必须能够回答：

- 它属于哪个架构层？
- 它属于哪个业务域？
- 它承担什么具体职责？
- 它应该落在哪个模块或文件？

如果无法确定归属，应先明确边界，再开始实现。

**为什么**

目录结构不是开发过程中的副产品，而是架构决策的具体体现。

没有明确的职责地图，文件通常会按照开发者当时最方便的位置生长，最终形成大量混合职责的模块。

**怎么验**

抽查最近新增的文件，每个文件都能明确对应职责地图中的一个位置。

如果找不到位置，应判断是：

- 职责地图缺少必要模块。
- 文件放置位置错误。
- 当前模块承担了不应该承担的职责。

## 5. 目录结构必须反映架构（MUST）

**要求**

目录结构必须与第 3 条的分层和第 4 条的职责地图对应。

目录应在业务实现之前建立。

目录命名必须有明确含义，不得长期依赖无边界的杂物目录。

以下目录需要重点控制：

- `utils`
- `common`
- `misc`
- `helpers`
- `shared`

这些目录并非禁止使用，但必须有明确的收纳范围。

如果一个目录持续积累多个不相关业务域的实现，应重新划分归属。

不得仅为了减少目录数量，将不同职责的代码集中放入同一个文件或目录。

**为什么**

目录树是开发者和 AI Agent 理解项目结构的第一入口。

如果目录不能体现实际架构，那么项目的组织规则就很难在日常开发中得到执行。

**怎么验**

- 仅查看目录树，就能大致还原项目分层和业务域。
- 核心模块有明确归属。
- 杂物目录不存在无边界扩张。
- 新增文件能够按照目录规则找到位置。

# 第二部分：文件组织与增长控制

## 6. 一文件一职责，创建时确定边界（MUST）

**要求**

每个文件必须有一个明确的主要职责，并且能够用一句话说明它的存在目的。

文件职责判断应重点考虑：

1. 文件是否只承担一个主要业务或技术职责。
2. 文件中的内容是否具有共同的变化原因。
3. 修改其中一部分是否经常迫使开发者同时理解另一部分。
4. 文件中的不同部分是否可以独立测试、替换或复用。
5. 是否已经存在明确的职责边界，却仍然被混合在一起。

当向现有文件增加新功能时，必须先判断：

- 是否属于该文件原有职责的自然扩展。
- 是否属于新的业务域。
- 是否具有独立变化原因。
- 是否需要单独测试或维护。

如果出现独立职责，应优先建立新文件或模块，不得仅以「以后再拆」为理由持续堆积。

注意：一文件一职责不等于一个函数一个文件，也不要求将高度相关、共同变化的代码强行拆散。

**为什么**

文件职责的核心不是代码数量，而是变化边界。

把多个独立职责放进一个文件，会导致修改影响范围扩大、测试困难、代码复用受限，并增加 AI 修改时的误操作概率。

**怎么验**

抽查文件时，能够清晰说明其主要职责、输入输出和依赖边界。

如果必须通过解释多个不相关功能才能说明文件用途，应重新审查其职责划分。

## 7. 增长阈值开工确定，触线必须审查（MUST）

**要求**

项目启动时，必须为主要代码角色确定合理的文件增长阈值。

阈值的确定方法：

1. 有既有代码时，统计同一角色文件的实际行数分布。
2. 优先以中位数、分位数和明显离群点作为判断依据。
3. 新项目没有历史数据时，使用保守初始值。
4. 第一个完整版本后，根据实际分布重新校准。

初始参考值：

| 文件角色 | 初始参考阈值 |
|---|---:|
| 业务实现 | 500 行 |
| 编排与胶水代码 | 800 行 |
| 生成代码 | 不使用普通行数阈值 |
| 测试代码 | 按测试组织策略管理 |

以上仅为缺乏历史数据时的参考值，不是所有项目的永久标准。

**触线处理规则：**

达到设定阈值时，必须进行职责审查。

审查后分为三种情况：

- 职责混杂：必须拆分，并在当前开发任务中完成。
- 职责清晰但存在可分离模块：评估拆分收益，合理拆分。
- 职责天然完整且拆分会增加复杂度：允许保留，但必须登记例外。

不得仅因为行数超过阈值，就机械地拆分文件。

同样，不得因为文件尚未达到阈值，就忽略明显的职责混杂。

**为什么**

行数是发现结构风险的信号，不是衡量代码质量的唯一标准。

真正需要避免的是：文件不断增长，职责却没有相应边界。

**怎么验**

- 采纳清单中有各角色的阈值。
- 超限文件经过职责审查。
- 未处理的超限文件必须登记。
- 职责混杂的文件不得以未达到行数阈值为由逃避拆分。

## 8. 按文件角色实施差异化管理（MUST）

**要求**

文件组织与增长管理必须区分角色，至少划分以下四类。

**A. 业务实现文件**

包括业务逻辑、领域服务、数据处理、平台操作等。

要求：

- 严格执行一文件一职责。
- 执行项目设定的增长阈值。
- 复杂业务按业务域和职责拆分。
- 不得将不同层的实现混合在一起。

**B. 编排与胶水文件**

包括：

- 程序入口。
- 模块注册。
- 路由注册。
- 命令分发。
- 依赖装配。
- 生命周期编排。

允许承担较多的连接与调度工作，但不得逐渐演变为业务逻辑实现文件。

**C. 生成代码与构建产物**

包括：

- 自动生成的类型定义。
- API 客户端。
- 代码生成器输出。
- 构建产生的文件。
- 自动同步的协议代码。

要求：

- 明确标注生成来源。
- 明确生成命令或工具。
- 明确源文件与生成文件之间的关系。
- 禁止直接修改可重新生成的产物。
- 根据项目需要决定是否纳入版本控制。

注意：代码生成器本身属于需要维护的源码，不等同于生成产物。

**D. 测试文件**

测试文件按照被测对象和测试目的组织。

原则上：

- 单元测试围绕被测模块组织。
- 集成测试围绕系统边界和交互流程组织。
- 端到端测试围绕用户场景组织。
- 测试数据、夹具和辅助工具独立管理。
- 不强制所有测试与源码采用完全相同的文件数量。

**为什么**

不同角色的文件具有不同的职责与增长规律。

如果使用同一套阈值和拆分要求，很容易误伤编排文件、生成代码和测试场景。

**怎么验**

- 项目采纳清单明确四类文件的管理方式。
- 生成代码有来源和生成方式标注。
- 编排文件不包含本应下沉的复杂业务实现。
- 测试目录能够区分测试对象和测试目的。

## 9. 命名必须体现职责和归属（SHOULD）

**要求**

目录名、模块名和文件名应尽量体现其业务域、职责或技术用途。

例如：

- `platform/dirs`
- `auth/microsoft`
- `components/launch`
- `services/download`
- `domain/account`

避免使用没有实际含义的命名：

- `new`
- `temp`
- `final`
- `misc`
- `other`
- `common2`
- `manager`（没有明确管理对象时）

不得使用作者、日期、版本号作为普通源码文件的主要命名依据。

**为什么**

命名是最低成本的代码索引。

合理的命名可以帮助开发者和 AI Agent 快速判断文件用途，减少不必要的全仓搜索。

**怎么验**

抽查目录和文件名，确认能够基本判断文件职责及所属模块。

# 第三部分：质量护栏与事实源

## 10. 验收基建先于业务代码（MUST）

**要求**

在第一批正式业务代码合并之前，必须建立项目的基础质量护栏。

根据项目类型至少配置：

1. 编译或构建检查。
2. 基础测试框架。
3. 代码格式检查。
4. 静态检查或类型检查。
5. CI 自动验证。

根据项目特点增加：

- 单元测试。
- 集成测试。
- API 契约测试。
- UI 组件测试。
- 端到端测试。
- 依赖安全检查。
- 构建产物检查。

不要求所有项目采用全部测试类型，但必须明确哪些检查是本项目的质量底线。

同时，必须保证空骨架可以通过基础构建和 CI 检查。

**为什么**

没有质量护栏，开发者很难安全地进行模块拆分、接口调整和结构重构。

测试与构建系统不是项目完成后的补充，而是保障项目能够持续演进的基础设施。

**怎么验**

- 空骨架可以正常构建。
- CI 能够执行并通过。
- 采纳清单写明各类检查的命令。
- 每个核心模块都有对应的验证方式。

## 11. 全局事实源必须提前确定（MUST）

**要求**

涉及全项目统一口径的内容，必须明确唯一事实源及其归属模块。

至少审查以下类型：

| 类型 | 需要确定的事实源 |
|---|---|
| 配置 | 全局配置定义与读取入口 |
| 路径 | 目录、文件及资源路径的统一管理 |
| 状态 | 跨模块共享状态的归属 |
| 类型 | 核心业务类型与共享协议 |
| 常量 | 跨模块使用的业务常量 |
| 网络 | API 地址、请求规范与客户端配置 |
| 存储 | 数据持久化与访问入口 |
| 权限 | 权限判断与身份验证入口 |
| 日志 | 日志格式、级别与输出策略 |

以上项目不要求全部建立独立模块，但必须明确哪些内容由谁负责。

对于同一项全局决策，不得允许多个模块各自维护一份独立真相。

需要区分：

- **唯一事实源：** 负责定义和维护真实口径。
- **使用方：** 通过接口或导入读取事实源。
- **派生数据：** 可以缓存或计算，但必须明确来源与更新机制。

**为什么**

事实源分散会导致配置冲突、路径不一致、状态重复维护以及业务口径不统一。

这类问题在项目早期不明显，但随着模块增加，修复成本会快速上升。

**怎么验**

- 采纳清单明确核心事实源的归属模块。
- 使用方通过统一入口获取数据。
- 不存在多个模块各自重复定义同一全局规则的情况。

## 12. 界面、样式与文案项目同样需要骨架（SHOULD）

**要求**

以 UI、页面和视觉内容为主要交付物的项目，也必须建立清晰的组织规则。

至少确定：

1. 基础组件与业务组件的边界。
2. 页面视图与业务逻辑的边界。
3. 状态管理与组件展示的边界。
4. 样式变量与组件样式的边界。
5. 文案与内容数据的组织方式。

样式系统应优先采用统一的 Design Token 或主题变量管理：

- 颜色。
- 字体。
- 间距。
- 圆角。
- 阴影。
- 动效参数。
- 主题模式。

不得在多个组件中随意重复定义同一全局设计值。

对于内容型项目，应根据实际情况区分固定文案、动态内容、页面模板和数据模型。

**为什么**

UI 项目的结构问题往往表现为样式散落、组件重复、状态归属混乱以及页面逻辑膨胀。

如果只治理后端代码而忽略前端结构，项目仍然会在另一种形式上失控。

**怎么验**

- 组件目录有明确分层。
- 全局设计变量有统一来源。
- 页面没有长期承载复杂业务实现。
- 相同设计语义不存在大量互相冲突的定义。

# 第四部分：结构变更与例外治理

## 13. 骨架调整必须先决策，再实施（MUST）

**要求**

项目骨架定版后，以下调整必须经过明确的结构变更判断：

- 增加、删除或合并架构层。
- 调整模块边界。
- 修改核心依赖方向。
- 大规模调整目录结构。
- 改变事实源归属。
- 修改文件组织策略。
- 调整核心质量护栏。

变更时必须说明：

1. 原有结构存在什么问题。
2. 为什么当前结构不再适用。
3. 新结构是什么。
4. 影响哪些模块。
5. 如何迁移和验证。

先更新项目采纳清单或架构决策记录，再实施对应代码调整。

小范围、符合现有职责地图的普通文件新增和移动，不需要每次都进行正式架构变更。

**为什么**

骨架不是永远不能改变，而是不能在没有决策的情况下随意改变。

既要防止结构失控，也要避免规范过度僵化，阻碍合理演进。

**怎么验**

- 结构性变更有对应的决策记录。
- 采纳清单与实际代码保持一致。
- 不存在通过先修改代码再追认规范的情况。

## 14. 例外必须逐项登记（MUST）

**要求**

确实无法遵守某项规范时，可以申请例外，但必须明确记录：

| 项目 | 内容 |
|---|---|
| 规则编号 | 违反哪条规范 |
| 涉及对象 | 具体文件、模块或目录 |
| 例外原因 | 为什么不能按常规处理 |
| 影响范围 | 可能带来的维护风险 |
| 复审条件 | 在什么情况下重新评估 |
| 处理方式 | 保留、拆分、替换或迁移 |

例外必须针对具体对象，不允许使用「本项目特殊」作为全局豁免理由。

例外不代表永久豁免，应在对应条件变化时重新审查。

**为什么**

工程规范允许合理例外，但必须让例外可追踪、可解释、可复审。

没有登记的例外最终会演变成新的默认规则。

**怎么验**

- 每项例外都有明确对象和理由。
- 实际超限文件与例外清单一致。
- 不存在未登记的长期违规项。

# 第五部分：执行与维护

## 15. AI Agent 必须遵守项目骨架，不得自行改变架构（MUST）

**要求**

凡参与项目开发的 AI Agent、编码助手或自动化执行程序，都必须将本规范及项目采纳清单视为项目结构约束。

执行任务时必须遵守：

**新增文件之前：**

1. 阅读相关目录和模块结构。
2. 确认文件所属架构层、业务域和职责。
3. 优先使用已有模块和事实源。
4. 不得为了方便直接在入口文件或杂物目录中堆积实现。

**修改文件之前：**

1. 了解文件现有职责。
2. 检查修改是否引入第二种独立职责。
3. 检查是否破坏原有依赖方向。
4. 检查是否重复实现已有能力。

**需要新增模块或调整架构时：**

1. 先说明现有结构为什么无法满足需求。
2. 提出目标落点与依赖关系。
3. 识别受影响的模块。
4. 必要时更新采纳清单。
5. 得到明确决策后再实施结构性调整。

**任务完成之后：**

1. 检查新增文件是否符合目录地图。
2. 检查文件是否违反增长阈值。
3. 检查是否产生重复事实源。
4. 执行对应测试与构建检查。
5. 更新受影响的工程文档。

AI Agent 不得以减少修改量、提高短期生成速度或降低当前任务复杂度为理由，绕过项目已经确定的架构规则。

**为什么**

AI Agent 具有快速生成代码的能力，但也容易在缺少结构约束时产生重复文件、职责混杂、错误依赖和临时性目录。

如果没有明确的工程边界，代码生成速度越快，后期治理成本可能越高。

**怎么验**

抽查 AI Agent 的代码提交：

- 文件落点是否正确。
- 是否重复创建已有模块。
- 是否擅自改变架构。
- 是否遵守事实源和依赖方向。
- 是否执行必要的质量检查。

## 16. 规范必须随项目演进，但不得无意义扩张（SHOULD）

**要求**

项目规范应当保持与实际代码结构一致。

以下情况出现时，应重新审查相关规范：

- 项目技术栈发生变化。
- 项目规模明显扩大。
- 新增独立业务域。
- 既有模块职责发生变化。
- 原有目录结构不再适用。
- 现有质量检查无法覆盖新增模块。
- 多次出现相同类型的结构违规。

规范更新应遵循：

1. 有真实问题才增加规则。
2. 已有规则能够覆盖的问题，不重复增加条款。
3. 不为极少发生的特殊情况建立复杂制度。
4. 优先修正不合理的原有规则，而不是无限增加补丁。
5. 规范变更必须保持与其他工程规范的一致性。

**为什么**

规范的目标是降低工程复杂度，而不是创造新的复杂度。

过度细化、重复约束和大量例外会增加开发者及 AI Agent 的理解成本。

**怎么验**

定期检查规范是否与项目实际结构一致，删除失效、重复或已经不再适用的约束。
