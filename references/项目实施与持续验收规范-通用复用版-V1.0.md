# 项目实施与持续验收规范（通用复用版）· V1.0

> **定位**：规定个人软件项目从接手、分析、实施、验证到交付和持续维护的执行方法，确保项目工作可控、过程可追溯、结果可验证。
>
> **适用范围**：新项目实施、已有项目重构、二次开发、功能迭代、缺陷修复、技术债务治理，以及由
> AI Agent 辅助或执行的开发任务。
>
> **体系关系**：本规范负责"项目工作如何推进与验收"；《项目启动规范》负责"项目开始前如何建立结构与边界"；《软件工程规范》负责"代码实现必须遵守什么工程规则"；《三端规范》负责"跨平台差异如何处理"。本规范引用其他规范，不复制其具体技术条款。
>
> **使用原则**：按任务风险和规模裁剪流程，不按大型团队的组织形式增加审批负担；但任何被声明为完成的工作，都必须有与其风险相称的验证证据。

------------------------------------------------------------------------

## 0. 规则等级、适用性与例外

### 0.1 规则等级

-   **MUST**：适用时必须满足；不满足不得宣称该阶段通过或任务完成。
-   **SHOULD**：默认采用；偏离时记录原因、影响和替代措施。
-   **MAY**：可按项目规模、风险和收益选择。

### 0.2 适用性判定

1.  开始任务时，先判断任务类型：新建、重构、二次开发、缺陷修复、维护或发布。
2.  再判断变更风险：是否触及用户数据、凭据、安全边界、持久化格式、公共接口、平台适配、构建发布链路或核心业务路径。
3.  不适用的阶段可以裁剪，但必须说明"不适用"的客观理由；不得把未执行写成已通过。
4.  小任务可以合并阶段记录，不得省略需求边界、变更审查和必要验证。

### 0.3 例外管理（MUST）

对本规范中的 MUST 条款确需偏离时，记录： - 偏离条款； - 客观原因； -
可能影响与风险； - 替代控制措施； - 决策者； - 失效时间或复查条件。

个人项目中的"决策者"可以是项目所有者本人。AI Agent
不得自行批准涉及数据丢失、安全降级、范围扩大或验收标准降低的例外。

### 0.4 证据原则（MUST）

计划、报告和验收结论必须区分： - **未执行**：没有执行相关检查； -
**已审查**：通过代码或配置审阅得出的判断； -
**已执行**：命令、测试或场景确实运行过； -
**已通过**：执行结果满足预先定义的通过条件； - **未通过 /
受阻**：结果不满足条件，或因环境、权限、依赖等原因无法完成。

不得把"看起来正确""理论上可行""代码已修改"写成"已验证"。

## 第一部分 项目接手与现状审查

### 1. 先识别项目状态，再决定实施方式（MUST）

任何非纯咨询类项目任务，在修改代码前必须识别项目当前状态。不得仅凭用户描述、目录名称或旧文档推断项目现状。

至少确认： - 项目入口、主要技术栈、构建与运行方式； -
当前分支、工作区状态及未提交变更； - 主要模块、关键依赖和数据流； -
当前功能行为与本次任务相关的调用链； -
现有测试、静态检查、构建和发布能力； -
已知限制、未解决问题及与本次任务相关的历史决策。

**为什么**：在不了解现状时直接修改，容易覆盖用户未提交工作、破坏既有行为，或重复实现已经存在的能力。

**怎么验**：实施记录中有项目现状摘要、检查过的入口和命令、发现的限制；工作区状态在变更前有记录。

### 2. 保护既有工作与数据（MUST）

-   修改前检查工作区；不得擅自覆盖、清理或重置用户已有改动。
-   不得执行可能丢失数据的命令，除非影响范围已确认并获得明确授权。
-   对数据库、用户文件、配置、凭据、生产数据及不可逆迁移，先确认备份、恢复方式和操作边界。
-   无法判断某项文件或改动是否属于用户工作时，先保留并询问，不得自行删除。

**怎么验**：变更前后状态可对比；危险操作有明确目标、影响说明和授权记录。

### 3. 建立可信基线（MUST）

在修改前，尽可能记录与任务相关的基线： - 当前能否构建、启动和运行； -
相关测试及静态检查结果； - 关键功能的现有行为； -
相关文件、模块和接口的现状； - 已存在的失败项及其证据。

基线失败必须区分"本次引入"与"修改前已存在"。不得把原有失败归咎于本次变更，也不得因基线失败而跳过本次可执行的验证。

**怎么验**：报告中有基线结果；无法建立基线时写明原因、受影响的验收项及替代验证方式。

### 4. 识别任务类型与改动性质（MUST）

开始实施前，明确本次属于哪一类或哪几类： - 新增能力； - 修改既有行为； -
缺陷修复； - 内部重构（预期外部行为不变）； -
依赖、框架或基础设施升级； - 数据结构、配置或身份迁移； - 平台适配； -
发布、部署或运维变更。

不同性质不能混为一谈。例如，重构的主要验收目标是行为保持；功能开发的主要验收目标是新增需求满足；迁移的主要验收目标是数据正确转换且可恢复。

**怎么验**：任务单中明确变更性质和主要验收目标。

## 第二部分 需求定义与范围控制

### 5. 将需求转化为可验证目标（MUST）

需求不能只写成"优化一下""修好""重构得更合理"。必须转化为可观察、可验证的结果，至少说明： -
当前问题或业务背景； - 期望结果； - 触发条件与使用场景； - 成功条件； -
不在本次范围内的事项； - 已知约束和依赖。

信息不足时，列出假设与待确认项。影响数据安全、接口兼容、用户可见行为或实施方向的关键歧义，未确认前不得擅自选择高风险方案。

### 6. 区分目标、方案与实现（MUST）

-   **目标**描述要解决的问题和结果；
-   **方案**描述实现路径及取舍；
-   **实现**描述实际代码、配置、数据和文档变更。

不得把某个实现方案伪装成用户需求；发现更简单或风险更低的方案时，应说明差异及影响，再决定是否调整。

### 7. 明确范围外与变更控制（MUST）

实施前建立范围外清单，至少列明： - 不需要修改的模块或功能； -
必须保持的外部行为、接口和兼容契约； -
不允许顺手进行的重命名、格式化、依赖升级或架构改造； -
不允许删除或替换的用户数据、配置及既有能力。

实施中发现必须扩围时，先说明原因、影响文件、风险、额外验证和成本，再取得项目所有者确认。不得自行把"顺手优化"并入交付。

### 8. 验收条件必须先于实施确定（MUST）

每项重要需求至少对应一个验收条件。验收条件应尽可能具体： -
输入或前置状态； - 操作或触发方式； - 预期结果； - 失败时的预期行为； -
验证方法与证据。

不得在实施结束后为了让结果通过而临时降低验收标准。确需调整时，记录原标准、新标准、调整理由和决策者。

## 第三部分 影响分析与实施计划

### 9. 先追踪完整调用链，再确定改动点（MUST）

对涉及既有功能的任务，先沿真实调用链确认： - 入口与触发源； -
数据来源及流向； - 状态所有者； - 核心决策点； -
外部副作用（文件、网络、进程、数据库、系统 API）； -
错误传播与用户反馈； - 相关测试和调用方。

不得仅根据搜索命中或单个文件推断完整行为。

### 10. 做变更影响分析（MUST）

至少检查以下相关影响面： - 直接依赖方和被依赖方； -
公共接口、数据结构与持久化格式； - 配置、凭据、缓存和用户数据； -
并发、异步任务与生命周期； - 平台差异与系统权限； - UI
展示与真实状态的一致性； - 构建、打包、安装、升级和卸载； -
日志、诊断与隐私； - 自动化脚本、文档和外部集成。

只列与本次任务相关的影响项；不相关项可标记"不涉及"，不得机械地为每个小改动生成冗长清单。

### 11. 先定义实施顺序与依赖关系（MUST）

把任务拆成可独立检查的工作项，并标明： - 前置条件； - 预期变更； -
依赖任务； - 可能影响； - 验收条件； - 回退或恢复方式。

优先处理会影响后续判断的基础问题，例如建立测试基线、确认数据契约、修复阻断构建的问题。不得在关键前置条件未满足时并行推进依赖它的工作。

### 12. 方案应比较风险与成本（SHOULD）

存在多个可行方案时，比较： - 正确性与安全性； -
对现有行为和数据的影响； - 实施复杂度与后续维护成本； - 兼容性； -
可测试性； - 回滚难度。

选择满足需求且总体风险可接受的最小充分方案。"最小"不等于只修表面症状；不得以少改代码为由违反《软件工程规范》的完整性要求。

### 13. 高风险变更必须有恢复方案（MUST）

涉及数据迁移、身份变更、持久化格式、凭据、批量文件操作、发布配置或不可逆操作时，实施前必须明确： -
影响对象与范围； - 备份或快照方式； - 恢复步骤； - 恢复失败时的处理； -
是否存在不可逆部分及其代价。

无法提供回滚时，必须明确说明"不可回滚"，并在执行前取得项目所有者确认。

## 第四部分 分阶段实施与变更纪律

### 14. 按可验收单元实施（MUST）

每个实施单元应足够小，使其变更目的、影响范围和验证结果可以独立理解。一个单元可以包含必要的代码、测试和文档，但不得把多个无关目标捆绑成一个难以审查的大改动。

### 15. 每个单元完成后立即验证（MUST）

完成一个可验收单元后，立即执行与其风险相称的检查，再进入依赖它的下一单元。不得把所有验证推迟到最后，导致问题来源无法定位。

### 16. 变更必须围绕已确认目标（MUST）

-   不擅自扩大需求；
-   不顺手升级无关依赖；
-   不借缺陷修复重写无关模块；
-   不删除暂时看似无用但尚未确认的兼容能力；
-   不以格式化、重命名掩盖功能性变更；
-   不为追求测试通过而删除或弱化有效测试。

确需调整范围，按第 7 条处理。

### 17. 保持变更可审查（SHOULD）

-   让每组变更具有单一、清晰的目的；
-   控制无关文件变动；
-   重要行为变化同时更新测试和必要文档；
-   对生成文件、锁文件和自动格式化结果说明来源；
-   保留足以理解变更的上下文，不用大段无关重排淹没实际差异。

### 18. 重构必须证明行为保持（MUST）

重构前先建立特征测试或等价验证，明确哪些行为必须保持。重构完成后，原有有效测试应继续通过；若测试因合理原因必须调整，应逐项说明测试变化不掩盖行为回归。

重构期间发现需要改变外部行为时，应拆成独立需求或经确认后重新定义验收目标，不得把功能变化藏在"重构"名义下。

### 19. 缺陷修复必须覆盖复现与防回归（MUST）

缺陷修复至少包括： - 可重复的复现步骤或能代表问题的输入； -
根因分析，不能只写表面现象； - 修复位置与影响范围； -
能失败地证明旧问题、并通过地证明修复有效的测试或场景； -
相关相邻路径的回归检查。

无法稳定复现时，记录已观察证据、推断与不确定性，不得声称根因已确认。

### 20. 暂停条件必须明确（MUST）

遇到以下情况应暂停相关实施，不得继续猜测： -
需求歧义会改变数据、权限或外部行为； - 发现用户未提交改动可能被覆盖； -
现有架构与计划假设明显不符； - 关键依赖、凭据或权限不可用； -
基线失败使结果无法归因； - 迁移或操作可能造成不可逆数据损失； -
验收条件互相冲突。

暂停时提交已确认事实、阻塞点、影响和需要的决策；不得用虚构假设继续推进。

## 第五部分 持续验证与质量门禁

### 21. 验证层级应与风险匹配（MUST）

按变更选择必要的验证层级： 1.
**静态审查**：代码、配置、依赖、差异与安全边界； 2.
**快速检查**：格式、Lint、类型检查、编译或构建； 3.
**单元测试**：纯逻辑、边界条件和错误路径； 4.
**集成测试**：模块、存储、进程或服务之间的协作； 5. **端到端 /
场景测试**：从用户入口验证完整行为； 6.
**真实环境验证**：真实操作系统、设备、服务、数据或安装环境。

不是每个任务都必须跑完全部层级；但省略某层时，应基于风险说明理由。涉及平台集成、设备能力、权限、安装升级或真实外部服务的变更，不能仅凭单元测试宣称真实环境可用。

### 22. 验证必须覆盖成功、失败与边界路径（MUST）

按功能性质至少考虑： - 正常输入与正常流程； -
空值、缺失值、越界值和畸形输入； - 权限拒绝、资源不存在和资源被占用； -
网络中断、超时、重试和重复触发； - 并发访问与状态竞争； -
中途失败、进程退出和恢复； - 用户取消、重复操作和快速连续操作。

只测试成功路径不足以证明功能可靠。

### 23. 验证结果必须可复查（MUST）

记录实际执行的命令、测试名称或场景、执行环境、结果和关键输出。日志、截图、报告应能对应到具体版本或变更，不得只写"测试通过"。

不得伪造命令输出、测试结果、设备验证、截图或构建状态。未执行的项目必须标为"未执行"，环境受阻必须标为"受阻"。

### 24. 失败项必须归类，不得静默忽略（MUST）

每个失败项至少归入： - 本次变更新引入； - 修改前已存在； -
环境或外部依赖导致； - 测试本身不稳定或失效； - 原因尚未确定。

记录证据、影响、是否阻断交付及后续处理。不得通过删除测试、跳过检查、屏蔽错误或无限重试把失败变成表面全绿。

### 25. 质量门禁不得被进度压力静默绕过（MUST）

对本次任务预先确定的阻断项，未通过就不得进入下一阶段或宣称完成。确需带问题交付，必须明确列出未通过项、影响、临时控制、责任归属和后续处理安排，并由项目所有者明确接受风险。

### 26. 持续回归，而非只测最后一次（SHOULD）

每个实施单元跑快速相关测试；阶段结束跑完整相关测试；发布前跑项目定义的发布门禁。测试失败后修复应重新执行受影响测试，并根据影响范围决定是否扩大回归。

### 27. 性能与资源变化必须有证据（SHOULD）

涉及启动时间、响应延迟、内存、CPU、磁盘、网络、功耗或大数据量处理时，建立可比较的基线，固定测试条件并记录多次结果。没有可比数据时，只能描述为"观察到改善"，不得宣称量化提升。

## 第六部分 阶段验收与交付

### 28. 阶段验收必须对照预先定义的条件（MUST）

阶段验收逐项核对： - 目标是否实现； - 范围是否受控； -
变更是否符合相关工程规范； - 必要验证是否执行并通过； -
失败项是否如实披露； - 文档、配置和迁移说明是否同步； - 证据是否留存。

阶段结论只能是：通过、附条件通过、不通过或受阻。不得用"基本完成""应该没问题"替代验收结论。

### 29. 最终交付必须包含完整变更说明（MUST）

交付报告至少包含： 1. 本次目标与范围； 2. 实际完成内容； 3.
主要文件、模块和数据变更； 4. 采用的方案及重要取舍； 5.
执行过的验证及证据等级； 6. 未执行、未通过和受阻项目； 7.
已知问题与剩余风险； 8. 配置、迁移、安装或升级注意事项； 9. 恢复 /
回滚方式或不可回滚声明； 10. 后续建议（区分必须处理与可选优化）。

### 30. 交付结论不得超过证据（MUST）

-   代码已修改，不等于功能已验证；
-   编译通过，不等于运行正常；
-   单元测试通过，不等于集成正常；
-   模拟环境通过，不等于真实平台或设备通过；
-   截图存在，不等于截图对应当前交付版本；
-   CI 通过，不等于所有发布和用户场景均通过。

结论必须逐项对应证据等级与验证范围。

### 31. 交付后保留可恢复状态（MUST）

交付时明确代码版本、提交或变更标识、构建产物、配置要求和数据版本。若项目没有版本控制或无法生成提交标识，应提供可识别的交付快照。不得只交付口头说明或无法对应到具体状态的文件集合。

### 32. 未完成事项必须进入后续清单（MUST）

未解决问题按阻断程度区分： -
**阻断项**：影响正确性、安全、数据完整性或核心使用，不能按正常完成交付； -
**高风险遗留**：可暂时交付，但必须明示影响和控制措施； -
**一般待办**：不影响本次验收的后续改进； -
**可选优化**：价值有限或纯外观工作，不得伪装成缺陷。

每项记录现象、证据、影响、建议处理方式和优先级。

------------------------------------------------------------------------

## 第七部分 持续维护与后续变更

### 33. 每次变更重新评估影响范围（MUST）

即使是小改动，也要确认它是否影响已有接口、数据、权限、平台差异、测试和发布链路。不得因为项目曾经通过验收，就默认后续改动没有回归风险。

### 34. 变更应复用既有事实源与架构边界（MUST）

实施前查找已有决策函数、配置来源、平台抽象、数据契约和公共组件。不得为图方便复制一份近似逻辑或建立平行事实源。若现有事实源确实不适用，应先评估并按相关规范调整架构。

### 35. 技术债务必须描述具体代价（SHOULD）

技术债务记录应包含： - 具体位置与现状证据； -
当前造成的实际代价或风险； - 触发条件与影响范围； - 建议处理方式； -
不处理的后果； - 优先级与复查条件。

仅仅"不够优雅""看起来旧"不构成高优先级债务。外观整理、命名统一等工作应与正确性、安全和数据风险分开。

### 36. 维护记录应反映真实状态（MUST）

需求、缺陷、决策、迁移、发布和验收记录应及时更新。旧计划不得继续标为当前计划；已撤销方案不得继续作为有效约束；过期风险应重新评估。文档与代码冲突时，先核实真实行为，再修正文档或代码，不得任选其一作为默认事实。

------------------------------------------------------------------------

## 第八部分 AI Agent 执行约束

### 37. Agent 必须先识别任务与读取适用规范（MUST）

执行前先判断任务类型和涉及领域，并读取适用的项目规范： -
项目结构或架构调整：读取《项目启动规范》相关条款； -
代码实现、重构、测试与依赖：读取《软件工程规范》； - Windows / macOS /
Linux 差异：读取《三端规范》； -
任务推进、范围、阶段验证与交付：执行本规范。

不得假定自己记得规范全文；项目内存在规范文件时，应以当前版本为准。

### 38. Agent 不得以自主性替代授权（MUST）

Agent
可以在已确认范围内自主完成低风险、可逆的实施步骤；以下事项必须先取得用户明确确认： -
扩大需求或改变验收目标； - 删除、覆盖或迁移用户数据； -
修改凭据、权限、安全策略或外部账户设置； -
执行不可逆或影响范围不明的操作； -
引入明显增加维护负担的依赖或基础设施； -
改变公共接口、持久化契约或用户可见行为，且超出已确认方案； -
降低质量门禁或接受高风险遗留。

### 39. Agent 必须先报告计划，再按阶段执行（MUST）

对涉及多个文件、多个模块、数据或架构的任务，先提交简明实施计划：现状、目标、范围、影响面、步骤、验收条件和风险。获得必要确认后实施。单文件、低风险、目标明确的小修复可以简化计划，但不得省略必要验证。

### 40. Agent 必须报告真实执行状态（MUST）

每个阶段报告： - 已完成； - 正在进行； - 未执行； - 失败或受阻； -
证据与验证结果； - 下一步。

禁止将推测写成事实、将计划写成完成、将审读写成测试、将本地模拟写成真实环境验证。

### 41. Agent 不得擅自清理或扩围（MUST）

不得为了让项目"更干净"而删除未确认的代码、配置、资源、文档、测试或用户数据；不得顺手重命名、全局格式化、升级依赖或改造无关架构。任何必要扩围按第
7 条处理。

### 42. Agent 必须交付可复查结果（MUST）

最终回复不能只说"已完成"。必须提供变更摘要、关键文件、验证命令与结果、未解决问题、风险和交付状态。无法执行的验证必须明确标注，不得用承诺替代证据。

## 附录 C：一页速查

1.  **先看现状，不先改代码**：识别项目状态、工作区、调用链和已有失败。
2.  **先定目标和范围**：需求可验证，范围外明确，扩围先确认。
3.  **先做影响分析**：接口、数据、权限、平台、并发、构建和发布都要按相关性检查。
4.  **先定验收，再实施**：完成条件不能在结果出来后临时降低。
5.  **分单元实施，分单元验证**：不把所有改动堆到最后统一检查。
6.  **重构证明行为保持，修复证明问题消失**。
7.  **验证分级，证据真实**：审读、编译、测试、真实环境验证不能混称。
8.  **失败必须披露**：不删除测试、不屏蔽错误、不伪造全绿。
9.  **交付必须说明风险和恢复方式**：未完成事项进入清单。
10. **Agent 不越权、不扩围、不虚报**：每个结论都能复查。
