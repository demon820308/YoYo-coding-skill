# 软件工程规范（通用复用版）·增强版

> 来源：原版 20 条来自一个跨平台桌面应用（Tauri＋Rust＋Vue）从首版到四轮整改的全部实战教训。本增强版在其上补入《通用软件工程规范 V2.0》中原版整片缺失的领域（安全与隐私、并发、迁移版本化、边界校验、幂等、可观测性、发布恢复、规则等级与例外管理）。
> 证据分级（诚实声明）：标[实证]的 20 条为原版原文，一字未改、力度未减，每条都有真实事故背书；标[补入]的 11 条来自体系完整性推导，尚未被事故实证，逐条标注了规则等级，采用时按其等级执行，待实证后再升格。V2.0 中稀释原版的措辞（禁补丁的「最小化修复」豁免、旧逻辑「标记为兼容路径」即可保留）**未采纳**，理由见文末对照说明。
> 用法：新项目开工前通读一遍定基调；整改时按条取用、写进工作单；每条都附了「为什么」与「怎么验」，验收不过即不算完成。

## 规则等级与例外管理（总则，先于一切条款）

- **MUST**：不满足不得验收。原版 20 条默认即此力度；[补入]条逐条标明等级。
- **SHOULD**：默认采用，偏离时说明理由与风险。
- **MAY**：按项目规模、风险与收益决定。
- **例外管理**：任何对 MUST 条的偏离，必须留字记录五项——偏离哪条、客观原因、风险、替代控制、批准人与失效/复查条件。口头同意、时间紧迫、「就这一次」不构成例外批准。
- **冲突处理**：两条规则在具体场景冲突时，不许静默选边；点名冲突、交决策者裁定、裁定结果留字。更具体、更可验的标准优先于更笼统者；正确性与安全底线优先于进度与形式。

## 第一部分 代码与架构

**1.[实证]禁止补丁式修改（总铁律）**
任何修改不许只改症状、叠例外/特判、新旧逻辑并存、或保留旧代码「以防万一」。必须在源头按完整逻辑单元重写，改完读起来像一次写成。
为什么：补丁式修改是所有长期腐化的源头 — 每一处「先这样绕过去」都会变成下一个 bug 的藏身地，且让后来的阅读者无法判断哪条路径是真的。
怎么验：审查 diff 时能指着一处说「这段是补丁」即不合格；新旧两套逻辑同时可达即不合格。

**2.[实证]环境事实只许运行时推导，差异只许收敛于一层**
平台、路径、架构、区域等环境相关事实，禁止写成字面量散落在业务代码里；必须运行时推导，且所有平台差异只许存在于一个专门的抽象层（如 platform 层）内。确需保留的字面量（如第三方公开 ID）须逐个登记理由。
为什么：写死的字面量在开发机上永远正确、在用户机上随机爆炸；差异散落时，修一处漏三处。
怎么验：全仓 grep 环境字面量，抽象层之外应为零（登记过的例外除外）；纯逻辑函数的平台相关输入应可注入、可单测。

**3.[实证]每项跨子系统决策只许一个事实源**
路径计算、特性判定、配置口径这类被多处使用的决策，必须收敛为单一函数/模块，全仓只许从它取结果，禁止各子系统自行拼算。
为什么：两处「算同一件事」的代码必然随时间分叉；更隐蔽的坏味道是 — 判定算出来了却只供界面显示，真正的行为路径另走一套，两边对不上，用户看到的状态和实际执行不一致。
怎么验：grep 该决策的计算点，应只剩事实源一处；显示层与行为层引用同一来源。

**4.[实证]业务核心不许依赖界面框架**
核心逻辑层禁止直接依赖 UI 框架本体；进度、事件、弹窗等需求通过抽象接口（端口）表达，由外壳层做适配器实现。
为什么：核心一旦绑上框架，就无法独立测试、无法复用，框架升级即全线震动。脱钩后核心可单独跑全部测试，是整个质量体系的地基。
怎么验：核心层依赖清单中无框架包；核心层测试可在无 UI 环境下全绿。

**5.[实证]结构限额：文件与函数的体积上限**
单文件建议 ≤ 700 行、单函数 ≤ 300 行（按语言惯例可调，但必须有线）。一个文件需要靠分隔横幅才能导航，即是超限信号；一个文件里装了多个独立产品/职责，必须按职责拆分。
为什么：体积本身不是罪，罪的是「多摊活挤一间屋」— 改一处怕碰另一处，测试无从下手，评审看不完。
怎么验：行数统计达标；拆分前后行为一致由既有测试证明（见第 18 条）。

**6.[补入·MUST]依赖必须可解释，且被持续管理**
新增第三方依赖必须说明必要性、维护状态、许可证与体积/运行风险；已有能力可提供的，不重复引入。锁文件必须入仓。依赖不是装完就完事：安全公告与大版本破坏性变更要有人盯，升级按第 13 条的 CI 门与第 18 条的特征测试走。
为什么：每一个依赖都是别人替你维护的一段供应链；无人管理的依赖会在某次安全公告或停更时一次性讨债。
怎么验：新增依赖在工作单或提交说明里有四项说明；仓库有锁文件；能说清最近一次依赖健康检查的时间与结论。

**7.[补入·SHOULD]接口契约与状态转换必须显式**
模块、服务与进程间的接口要写清契约：输入、输出、错误形态、兼容承诺。实体的状态转换必须显式定义（合法转换的集合），禁止靠散落的条件判断拼出隐式状态机。
为什么：没有契约的接口，调用方只能靠读实现猜语义，改一端炸另一端；隐式状态迟早走到一个没人定义过的状态里出事。
怎么验：关键接口有可查的契约说明；状态实体能列出全部合法转换，非法转换被拒绝且有对应用例。

## 第二部分 正确性与数据

**8.[实证]完整性校验要用权威哈希，不许用「存在＋大小」冒充**
凡上游提供校验值（哈希）的文件，下载/导入后必须验；「文件存在且大小相等」不构成有效性证明。经第三方镜像或不可信通道获取的文件，标准只能更高不能更低。「已存在则跳过」的复用逻辑必须先过校验，否则坏文件会永久驻留。
为什么：大小相同而内容损坏/被篡改的文件能通过一切廉价检查，直到在最难排查的环节爆成崩溃。
怎么验：备一个「内容篡改但大小不变」的样本，系统必须识别并自愈（重下/拒绝），有对应用例。

**9.[实证]用户数据的落盘必须原子写**
配置、凭据、存档等「写坏即丢用户状态」的文件，一律先写临时文件再原子替换，禁止直接覆盖写。
为什么：直接覆盖写在崩溃/断电时留下截断文件，代价是用户设置与登录态清零；而下载缓存这类可再生文件反而往往做得规整 — 轻重倒置是常见盲区。
怎么验：审查所有写用户状态的路径，应统一走同一原子写工具函数。

**10.[实证]界面必须与真实状态对账**
凡界面展示的是外部状态的镜像（文件系统、服务端数据），必须有对账机制：回到前台/切页时刷新；选中项失效时自动修剪并给用户明确提示；关键动作执行前先验目标存在，不存在给人话说明而不是抛底层错误。仅「应用内操作同步更新界面」不构成对账 — 用户绕过应用直接改外部状态是常态，不是例外。
为什么：幽灵条目（已删的东西还显示、还能点、点了才报错）是最伤信任的一类缺陷，且自测时极易漏掉，因为开发者习惯在应用内删除。
怎么验：手测脚本包含「在应用外增删条目 → 回到应用」的正反场景。

**11.[实证]错误信息说人话**
面向用户的错误必须点名对象与原因（「版本 X 已不存在，已为你刷新」），禁止把底层 IO/系统错误原文直抛给用户。底层细节进日志，不进弹窗。

**12.[补入·MUST]一切外部输入必须在边界处校验**
用户输入、文件、网络响应、外部进程输出，在进入系统的边界处一次性校验类型、范围与编码，不合法即拒绝，不许带着脏数据进核心后再沿路打补丁式校验。拼接命令、查询语句、文件路径时用参数化/结构化接口，禁止字符串拼接受信数据（注入防线就在这一条里，不另设）。
为什么：边界一处校验，全系统受益；散点校验必然漏一处，而漏的那处就是注入与崩溃的入口。
怎么验：备畸形输入与注入样本集（超长、越界、特殊字符、路径穿越、注入片段），边界处全部被拒且有记录；核心内部无重复的同类校验散点。

**13.[补入·MUST（涉共享可变状态时）]并发访问必须有一致性策略**
凡多线程、多进程或异步回调会碰同一份可变状态，必须先定策略再写码：串行化（锁/队列/单写者）、事务、或不可变数据＋原子替换，三选一并写明。「大概不会同时发生」不算策略。
为什么：竞态 bug 不可复现、不可调试，本地测一百次不犯，上线第一天就犯；先定策略的成本远低于事后抓鬼。
怎么验：共享状态清单逐项标注所用策略；高频竞态路径有并发用例或压测记录。

**14.[补入·MUST]数据结构与迁移必须版本化**
持久化的数据结构必须带版本号；结构变更必须有从旧版到新版的迁移路径，迁移可重复执行不产生二次伤害。与第 28 条分工：第 28 条管「要不要迁移」的决策，本条管「决定迁移后怎么做对」的机制。
为什么：没有版本号的数据，升级时无从判断它是哪一代的，只能靠猜；猜错一次就是批量丢用户数据。
怎么验：迁移路径有「仅旧数据/仅新数据/新旧并存」三态测试；迁移在样本数据上先演练再上真实数据；不可回滚的迁移必须在执行前明示代价并经确认。

**15.[补入·SHOULD]关键操作必须幂等或防重复执行**
支付、提交、发送、导入、任务触发这类「做两次就出事」的操作，必须设计成重复执行结果一致（幂等键/去重/状态前置检查）。重试机制只能建立在幂等之上。
为什么：网络会抖、用户会连点、队列会重投——重复执行是常态，不是异常；不防重的系统迟早重复扣款、重复发货、重复建档。
怎么验：同一请求连发两次（或模拟重投），最终状态与执行一次一致，有对应用例。

## 第三部分 安全与隐私（本部分全部为[补入]）

**16.[补入·MUST]凭据与敏感信息不进代码、仓库与日志**
密钥、令牌、密码一律经环境变量、平台保险库或受限令牌注入，禁止硬编码、禁止提交入仓、禁止打进日志与报错信息。已经进过仓库或截图、聊天等公开面的凭据，一律视同已泄露：立即撤销/轮换，而不是删掉记录假装没发生（本工作区 2026-11-04 即按此收口过一次截图露出的密钥）。
为什么：仓库与截图的传播范围不可控，凭据一旦露面，唯一安全的假设就是别人已经拿到了。
怎么验：全仓 grep 凭据特征零命中（登记过的占位符除外）；日志样本无敏感字段明文；能说清每个凭据的注入方式与轮换路径。

**17.[补入·MUST]最小化：授权、收集、保留都只取必要**
权限只给完成任务所需的最小范围，能给单项受限令牌就不给全权密钥。用户数据只收集功能必需的，只保留必需的期限，删除要有真实可达的路径。
为什么：没拿到的数据永远不会泄露，没给出的权限永远不会被滥用；最小化是唯一在事故发生前就生效的安全措施。
怎么验：权限与令牌清单逐项能说清「为什么需要这一项」；数据清单逐项能说清收集目的与保留期限，说不清的删。

## 第四部分 测试、验证与性能

**18.[实证]重构之前先落特征测试**
拆分、搬家、换实现之前，先用测试把现有行为钉死（黄金快照、夹具输入输出对）。重构的验收标准就是这批测试**原样**通过 — 快照本身即行为等价证明，不必再做人肉逐项比对。
为什么：没有测试网的结构调整，本质是拿用户的运行时当测试环境。
怎么验：测试先行提交在拆分提交之前；拆分提交中测试文件零修改。

**19.[实证]测试要覆盖最常改的路径，而非最好测的路径**
纯逻辑好测，但事故多发于 IO、解析、参数构建。解析类逻辑喂录制的真实样本 JSON 即可离线测；文件操作用临时目录测；参数构建做黄金快照。网络与真实进程不进单元测试。
怎么验：看测试分布对照改动频率 — 最高频改动的文件若测试最少，即为补网优先级第一位。

**20.[实证]验证结论必须标注证据等级，不许冒充**
代码审读、编译通过、测试全绿、真机实测是四个不同等级，下结论时用哪级说哪级。CI 全绿只证明「能构建＋单测过＋能打包」，永远不等于「在真实设备上可用」。
为什么：把低等级证据说成高等级结论，是验收环节最常见的自欺，且会在最关键处（真机、真实数据）翻车。
怎么验：报告中的每条结论应能反查到它依据的证据类型；无留档的验收项写明「未留档」，不许默认通过。

**21.[实证]轻量 CI 每次推送必跑，重型构建按需**
每次 push/PR 跑快速门（测试＋类型/编译检查＋前端构建，数分钟内）；打包发版等重型流水线只在打 tag 时跑。没有 CI 兜底的主干提交等于裸奔 — 结构越大越如此。
怎么验：CI 配置与最近运行记录，两者都要看（配了没跑、跑了没绿都不算数）。

**22.[实证]性能修复必须留数字基线**
性能优化以「固定夹具＋开关打点＋多次取中位数」的方式留档：夹具规模写明、结果文件入仓、设一条达标线。没有前后数字的性能结论一律视为未验证。
为什么：无基线则无回归感知 — 某次顺手改动把启动拖慢一倍，也要等用户投诉才知道。

**23.[补入·MUST]测试必须可重复、可隔离**
测试不许依赖执行顺序、真实网络、当前时刻或未播种的随机数；单个测试可独立重跑，失败可复现。偶发失败（flaky）是缺陷，要登记修复，不许用「重跑就过了」掩盖。
为什么：不可重复的测试全绿时给假信心、红了时给假警报，两次之后团队就学会无视它，测试网等于自废。
怎么验：乱序执行与单跑指定用例均通过；测试环境不访问真实外部服务（录制样本与本地假件除外）。

**24.[补入·SHOULD]可观测性必须支持定位**
关键路径要有结构化日志：关键动作的起止、失败环节、足够定位的上下文与可关联的标识。出了问题只靠用户描述、没有日志可查，等于没有观测。日志纪律受第 16 条约束：可定位，但不许打敏感明文。
为什么：第 11 条把底层细节赶进了日志，日志就必须真的接得住——否则错误既没给用户看明白，也没给排查留线索，两头落空。
怎么验：模拟一次关键路径失败，仅凭日志能说清失败发生在哪一步、因为什么。

## 第五部分 注释与文档

**25.[实证]注释只写为什么，不写是什么**
命名已说清的不许用注释复述；禁止章节横幅注释；禁止在代码里写设计出处叙事（出处只在 README 写一句总述）；禁止引用外部文档的条款编号（规则本身就地写清）。反之，解释「为什么、约束、踩过的坑、外部规则与直觉不符处」的注释是资产，清理时误删即不合格。
为什么：复述型注释制造「注释很多」的假象，同时稀释真信息；读代码的人被迫在噪音里找信号，最终学会不看注释 — 真注释也随之失效。
怎么验：注释总量与四类噪音（复述、横幅、叙事、条款号）可 grep 计数，整改前后对比即证据。

**26.[实证]文档日期与数据必须真实**
CHANGELOG、报告、基线数据中的日期与数字必须与事实一致，宁可查证后写，不许顺手编一个「看起来合理」的值。自动生成的提交列表不能冒充发版说明 — 发版说明由人写用户可读的条目。
为什么：一份文档被发现有一处造假，整份文档的可信度归零；而这类文档的全部价值就是可信。

**27.[实证]验收证据随交付留档**
凡验收标准里写了的证据（计数、测试输出、运行链接、截图），必须随交付物留档。涉及视觉的改动（改名、样式替换）尤其注意：这类改错往往不报错、只静默失效，截图对照是唯一可靠验收，不许以「构建通过」替代。

## 第六部分 变更、兼容与比例

**28.[实证]身份与存储类变更必须显式决策**
改包标识、配置文件名、数据结构版本时，二选一并写进发版说明：做一次性迁移，或裸改并明示用户代价（如需重新登录一次）。禁止默默裸改 — 那等于替用户决定丢数据。同时按比例原则：迁移的成本必须有受益人，受益规模为零时不建迁移 machinery，但决策本身要留字。
怎么验：发版说明中能检索到该变更与用户代价；迁移路径有「仅旧/仅新/新旧并存」三态测试。

**29.[实证]清理前先分清「兼容契约」与「品牌残留」**
与外部系统互通的字符串（协议前缀、互操作格式、对第三方服务的兼容标识）是功能契约，不是残留，清理时必须列入保留清单、误改即功能回归。真正的残留只指自有标识。清单化：清理清单与保留清单同等强制。
为什么：全仓搜关键字一键替换最容易误伤的，就是这些「长得像残留的契约」。

**30.[实证]按价值分类，不让外观工作冒充债务**
改名、整洁、统一风格类工作对运行零影响，应明确标为可选/外观项，与功能正确性、数据安全类债务分开排期、分开汇报。做与不做都正当，但不许混在「问题清单」里制造紧迫感，也不许挤占正确性工作的资源。

**31.[补入·MUST]发布必须留版本、变更与恢复信息**
每个正式版本必须四件齐：版本号、人写的用户可读变更说明（受第 26 条约束）、已知问题、恢复/回滚路径（或明示不可回滚及其代价）。
为什么：出事时第一个问题永远是「这版改了什么、怎么退回去」；这两样若在发版时没留，事故现场现挖就来不及。
怎么验：任取一个已发版本，能在一处查齐四项；回滚路径至少在样本环境演练过一次，或注明未演练。

## 第七部分 工作单写法（给执行方时套用）

每条工作项按五段写，缺一不可：
1. **现状证据**：实测数字与位置（行数、计数、命中清单），不写形容词；
2. **整改要求**：要改成什么样，含明确的切分/命名/上限；
3. **验收标准**：可执行的检查（grep 计数、测试名单、场景脚本、截图要求），执行方自证；
4. **范围外**：不许顺手做的事、必须保留的清单 — 执行方扩围须经提出方裁定，不得自认「已获批准」；
5. **交付格式**：报告结构与证据清单。

不可跳过的步骤用抗压措辞：铁律一句话＋把常见借口（「就这一次」「对方在催」「我很确信」）逐条点名为借口＋声明优先级（规则压过催促、格式与场景压力），无例外。平实措辞（「应该、尽量」）在压力下必然被跳过。

逐项独立提交、逐项验收；一项未验完不开下一项的合并。执行方自称的「已获批准/已完成」一律以可复查的证据为准，不采信口头结论。

[补入]执行纪律一条：**不得伪造执行结果**。声称跑过的命令、测试、构建、真机验证，必须有真实输出可复查；把未执行的写成已执行、把审读结论写成实测结论，一经发现整批交付退回，且该执行方后续交付的证据等级默认降一级审查。这是对第 20 条（结论标证据等级）在执行方一侧的对等约束。
