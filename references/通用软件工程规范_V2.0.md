# 通用软件工程规范 V2.0

> **定位**：适用于不同技术栈、不同规模的软件项目，以及由人类或 AI
> 编程智能体执行的开发、重构、整改与交付任务。
>
> **核心目标**：让每一次变更都有明确边界、有可验证依据、可追溯、可回滚；避免局部修复演变为系统性技术债务。
>
> **使用方式**： 1.
> 新项目启动时，确定本规范的适用条款，并形成项目级技术规范。 2.
> 每次开发或整改前，编写任务工作单，明确现状、目标、验收、范围外事项和交付证据。
> 3. 执行过程中按规则验证；未达到验收标准的事项不得标记为完成。 4.
> 对不适用或确需偏离的规则，记录理由、风险、批准人和有效范围，不得静默绕过。

------------------------------------------------------------------------

## 0. 规则等级与适用原则

本规范中的要求分为三级：

-   **MUST（强制）**：默认必须遵守。未满足不得验收；确需例外时，必须按"例外管理"记录并获得明确批准。
-   **SHOULD（推荐）**：默认采用。偏离时应说明原因、影响和替代措施。
-   **MAY（可选）**：按项目规模、风险、技术栈和实际收益决定是否采用。

### 0.1 比例原则

工程措施应与风险和项目规模相匹配。不得为了形式完整而引入没有明确受益对象的复杂机制，也不得以"项目很小"为由省略数据安全、用户隐私、正确性和可恢复性等基本要求。

### 0.2 例外管理

任何对 MUST 规则的偏离，必须记录：

1.  具体规则及偏离范围；
2.  不遵守的客观原因；
3.  可能产生的风险；
4.  临时替代控制措施；
5.  批准人、记录日期及复查/失效条件。

口头同意、执行方自行判断、时间紧迫或"只这一次"均不构成批准。

# 第一部分：架构与代码质量

## 1. 禁止症状式补丁，优先修复根因

**等级：MUST**

禁止通过不断叠加特判、重复逻辑、隐藏分支或保留两套可达实现来掩盖根因。修改应落在正确的责任层和完整的逻辑边界内。

允许有明确边界的最小化修复，例如修复单一条件判断、补充必要的输入校验或处理一个确定的边界错误；不要求为了形式上的"整体重写"而扩大变更范围。

**验收：** - 能说明故障根因及修复位置； -
不存在为绕过问题而新增的重复路径； -
相关旧逻辑已删除、替换或明确标记为兼容路径； -
修改范围与风险相称，未无故扩大。

## 2. 环境差异集中管理

**等级：MUST**

平台、操作系统、架构、路径、区域、运行时能力等环境事实，不得以未经管理的字面量散落在业务代码中。应通过平台适配层、配置层或运行时能力检测统一提供。

公开协议常量、第三方
ID、固定格式标识等允许保留，但必须能说明其来源和稳定性。

**验收：** - 搜索环境相关字面量并审查命中位置； -
平台差异集中在约定层； - 纯业务逻辑可通过参数注入环境依赖并独立测试； -
不把"当前开发机配置"误当作所有用户环境的事实。

## 3. 跨模块决策必须有单一事实源

**等级：MUST**

同一业务决策、权限判定、路径计算、状态定义、配置口径或功能开关，应由一个明确模块负责。展示层、执行层、后台任务和
API 不得各自复制计算规则。

**验收：** - 能定位该决策的唯一权威实现； -
所有调用方复用同一结果或接口； - UI 展示状态与真实行为使用同一事实源； -
对关键决策存在正反边界测试。

## 4. 业务核心与外部框架解耦

**等级：SHOULD**

核心业务规则应尽量不直接依赖 UI 框架、网络框架、操作系统 API
或具体数据库实现。通过接口、端口、适配器或依赖注入表达外部能力。

小型脚本、简单展示型应用或框架本身就是业务核心的项目，可按比例原则简化，但应避免无意义的抽象层。

**验收：** - 核心规则可在不启动完整 UI 的情况下测试； -
外部依赖边界清晰； - 更换适配器不需要重写核心业务规则。

## 5. 模块职责与复杂度控制

**等级：SHOULD**

文件行数和函数长度是预警指标，不是机械拆分命令。可将单文件约 700
行、单函数约 300 行作为初始警戒线；项目可根据语言惯例调整。

出现以下情况时，应优先考虑拆分： - 一个模块承担多个独立业务职责； -
修改一个功能经常影响无关功能； - 函数存在过多分支、状态或副作用； -
依赖关系难以理解或测试； - 文件必须依靠大量章节横幅才能导航。

**验收：** - 拆分依据是职责和耦合，而不只是行数； -
拆分前建立行为基线； - 拆分后相关测试通过； -
没有为了降低行数而制造过度碎片化。

## 6. 依赖关系必须可解释

**等级：MUST**

模块依赖方向应清晰，不得通过循环依赖、隐式全局状态或跨层直接访问破坏架构边界。新增第三方依赖应说明必要性、维护状态、许可证、体积或运行风险。

**验收：** - 依赖图中不存在未经批准的循环依赖； -
新增依赖有用途和风险说明； - 核心模块没有反向依赖外层实现； -
不重复引入已有依赖可提供的能力，除非有明确理由。

# 第二部分：数据正确性与持久化

## 7. 完整性校验必须使用可信依据

**等级：MUST（适用于下载、导入、更新及其他完整性敏感数据）**

上游提供哈希或签名时，必须校验。文件存在、大小相等或扩展名正确，均不能替代内容完整性验证。

对来源不可信或经第三方镜像获取的内容，应采用与风险相匹配的校验措施。若没有权威哈希，应明确采用的替代验证方式及其局限。

**验收：** - 有内容损坏或篡改样本； -
校验失败时拒绝使用，并按场景重试、重下或提示； -
"已存在则跳过"之前先校验； - 校验算法、哈希来源和失败行为有记录。

## 8. 用户关键数据必须具备安全写入机制

**等级：MUST**

配置、凭据、存档、用户创作内容等不可轻易丢失的数据，应使用临时文件写入、刷新并原子替换等安全策略。具体实现须考虑目标文件系统、平台语义和权限。

数据库数据应使用事务及适当的提交策略。不得把"调用了写入函数"视为持久化成功。

**验收：** - 写入失败或进程异常时，原数据不会被半截内容直接覆盖； -
临时文件清理策略明确； - 关键写入错误可被上层识别； -
数据库多步变更有事务边界。

## 9. 并发访问必须有一致性策略

**等级：MUST（存在并发读写时）**

多个线程、任务、进程或设备可能同时修改同一数据时，必须明确并发控制策略，例如锁、事务、版本号、乐观并发控制或冲突合并。

不得默认"用户不会同时操作"或"任务总会按顺序完成"。

**验收：** - 明确共享数据及其写入者； - 并发冲突有确定处理方式； -
关键路径有并发测试或可重复的验证脚本； -
不会因竞态造成数据覆盖、重复执行或状态错乱。

## 10. 数据结构与迁移必须版本化

**等级：MUST（持久化结构发生不兼容变化时）**

数据库、配置文件、缓存索引及其他持久化结构发生不兼容变化时，必须明确版本识别和迁移策略。迁移应考虑失败恢复、重复执行和旧版本数据处理。

**验收：** - 有旧版本样本； -
测试旧数据升级、新数据启动及迁移失败场景； -
迁移具备事务或备份/恢复策略； - 不兼容变更的用户影响写入发布说明。

## 11. 输入数据必须在边界处校验

**等级：MUST**

来自用户、文件、网络、第三方服务、插件或进程间通信的数据，进入业务核心前必须验证类型、范围、格式、长度及权限条件。不得仅依赖
UI 控件限制输入。

校验失败应产生可识别的业务错误，不得继续以不确定状态执行。

**验收：** - 覆盖空值、缺字段、错误类型、越界值、超长内容和恶意格式； -
文件解析有大小、深度或资源消耗限制； -
不可信数据不会直接进入命令执行、路径拼接或数据库语句。

## 12. 用户数据与界面状态必须对账

**等级：MUST（界面展示外部可变状态时）**

界面镜像文件系统、服务端数据、设备状态或其他外部状态时，必须有刷新和失效处理机制。回到前台、切页、重新连接或执行关键操作前，应按场景重新确认状态。

仅在应用内部同步更新界面，不构成完整对账机制。

**验收：** - 在应用外增删或修改数据后，回到应用能正确反映； -
失效选中项会自动修剪或提示； - 关键动作执行前再次确认目标有效； -
失败提示面向用户可理解。

## 13. 错误必须分层处理

**等级：MUST**

底层错误应保留足够上下文供日志和诊断使用；面向用户的提示应说明发生了什么、影响对象、用户可采取的下一步。不得把原始
IO、堆栈、SQL 或系统错误直接作为唯一用户提示。

**验收：** - 错误有稳定分类或错误码（适用时）； -
日志包含诊断上下文但不泄露敏感信息； -
用户提示不要求用户理解底层实现； - 不得静默吞掉影响结果的错误。

# 第三部分：安全与隐私

## 14. 凭据与敏感信息不得进入代码仓库

**等级：MUST**

密码、访问令牌、私钥、签名材料、生产环境凭据及其他敏感信息不得硬编码进源代码、测试样本、日志、截图或公开文档。应使用受控配置、密钥管理服务或操作系统安全存储。

**验收：** - 仓库及构建产物经过适当的密钥扫描； -
示例配置只包含占位值； - 凭据泄露时有撤销和轮换流程； -
日志与错误上报经过敏感字段清理。

## 15. 权限必须遵循最小授权

**等级：MUST**

应用、服务、插件、子进程和自动化代理只获取完成任务所需的最小权限。高风险操作应有明确授权边界；不能因为技术上可调用就默认允许调用。

**验收：** - 权限清单与实际能力一致； -
文件、网络、系统命令和账户访问有边界； -
高风险操作有授权、确认或策略控制； - 权限拒绝时程序能安全失败。

## 16. 外部输入与执行操作必须防注入

**等级：MUST**

不得把不可信输入直接拼接为 shell
命令、SQL、脚本、模板表达式或文件路径。优先使用参数化接口、结构化
API、允许列表和安全路径解析。

**验收：** - 对命令执行、SQL、模板和路径操作进行专项审查； -
覆盖路径穿越、命令注入和查询注入样本； -
外部内容不得被当作可信指令执行； - 失败时不扩大权限或降级为不安全执行。

## 17. 隐私数据遵循最少收集与最短保留

**等级：MUST（涉及个人数据时）**

只收集实现功能所必需的数据，明确用途、访问范围、保存位置、保留期限和删除机制。调试日志、遥测、崩溃报告和
AI 请求不得默认携带不必要的个人信息。

**验收：** - 数据流向和存储位置可说明； - 日志与上传内容经过脱敏； -
数据删除和导出行为有定义； - 第三方服务的数据使用边界经过评估。

## 18. 第三方依赖必须持续管理

**等级：SHOULD**

对直接和间接依赖关注已知漏洞、维护状态、许可证兼容性和来源可信度。生产依赖升级应有变更记录和回归验证。

**验收：** - 依赖清单可生成； - 重要依赖有版本锁定策略； -
安全扫描发现的问题有处置记录； - 不以盲目升级替代风险评估。

# 第四部分：接口、状态与系统边界

## 19. 模块接口必须定义契约

**等级：MUST**

跨模块、跨进程、跨服务或对外 API
的接口，应明确输入、输出、错误、权限、超时、重试和兼容性要求。不得依赖调用双方未声明的隐式约定。

**验收：** - 接口字段、类型和语义有定义； - 错误与边界行为明确； -
关键接口有契约测试或等效验证； - 变更调用方和被调用方均经过影响分析。

## 20. 状态转换必须明确

**等级：MUST（存在多状态业务对象时）**

复杂业务状态应定义合法状态、转换条件、失败状态及恢复路径。不得仅靠多个布尔变量拼凑互相矛盾的状态。

**验收：** - 状态图或等效说明能表达主要路径； - 非法转换会被拒绝； -
异常中断后可恢复或明确失败； - UI 展示与业务状态机一致。

## 21. 网络与外部进程必须设置边界

**等级：MUST（存在网络或外部进程调用时）**

网络请求和外部进程调用必须考虑超时、取消、退出码、输出大小、重试条件和资源释放。重试必须区分可重试错误与不可重试错误，避免重复执行非幂等操作。

**验收：** - 请求与进程不会无限等待； - 取消操作能够传递到适当层级； -
重试有次数、间隔和条件限制； - 资源在成功、失败和取消路径中均能释放。

## 22. 关键操作应具备幂等或防重复机制

**等级：SHOULD**

支付、创建订单、导入、发布、迁移、删除、任务提交等可能被重复触发的操作，应通过幂等键、状态检查、唯一约束或去重机制避免重复副作用。

**验收：** - 明确哪些操作不可重复； - 重复请求不会产生非预期副作用； -
超时后重试有确定语义； - 失败与成功状态可区分。

# 第五部分：测试、验证与性能

## 23. 重构前先建立行为基线

**等级：MUST（重构或替换现有行为时）**

拆分、迁移、换实现或优化之前，应使用现有测试、黄金样本、快照或可重复场景记录当前行为。若发现旧行为本身有缺陷，应先明确哪些行为需要保留、哪些需要改变。

**验收：** - 基线建立在重构之前； - 基线输入和预期结果可复现； -
测试变更有理由，不得为了让新实现通过而随意改写预期； -
行为变化被明确记录。

## 24. 测试优先覆盖高风险与高变更频率路径

**等级：MUST**

测试策略应根据风险、变更频率和故障代价制定，而非只覆盖容易测试的纯逻辑。重点关注
IO、解析、权限、参数构建、数据迁移、并发和异常恢复。

**验收：** - 测试分布与风险清单相匹配； - 解析逻辑使用真实或脱敏样本； -
文件操作使用隔离的临时目录； -
网络和真实进程通过集成测试、模拟服务或专用环境验证； -
高风险路径有明确测试责任。

## 25. 测试必须可重复、可隔离

**等级：MUST**

自动化测试不得依赖开发者个人机器上的偶然状态。测试应控制输入、时间、随机数、环境变量、文件目录和外部服务依赖。

**验收：** - 测试可在干净环境运行； - 测试之间不共享未清理状态； -
不依赖真实生产账户或生产数据； -
失败时能定位原因，而非只得到不稳定的偶发结果。

## 26. 验证结论必须标注证据等级

**等级：MUST**

代码审查、静态检查、构建通过、自动化测试、真实环境验证和用户验收是不同证据。不得用低等级证据冒充高等级结论。

建议报告使用以下证据标签：

-   **E1：代码审查**------已检查代码和变更范围；
-   **E2：静态检查/构建**------Lint、类型检查、编译或打包通过；
-   **E3：自动化测试**------注明测试类型、数量和结果；
-   **E4：真实环境验证**------注明设备、系统、数据和操作场景；
-   **E5：交付验收**------按用户场景完成验收并留存证据。

**验收：** - 每项结论标明证据等级； - 未执行的检查明确写"未执行"； -
无留档的项目明确写"未留档"； - CI 通过不等于真实环境可用。

## 27. CI 必须真正运行并检查结果

**等级：SHOULD**

有持续集成条件的项目，应在每次推送或 PR
时运行轻量检查，包括测试、类型/编译检查和必要的构建。耗时较长的打包、签名或发布流程可按触发条件执行。

**验收：** - 检查配置存在； - 最近一次运行记录可查； -
失败会阻止合并或触发明确处理； - 不以"配置了 CI"冒充"CI 已通过"。

## 28. 性能优化必须有可比较基线

**等级：SHOULD**

性能问题应通过固定数据集、明确环境、重复测量和统计口径验证。至少记录优化前后数据；适用时使用中位数、分位数、吞吐量、内存峰值或启动耗时。

**验收：** - 记录硬件、系统、数据规模和测试方法； -
优化前后采用相同条件； - 结果文件或报告可追溯； -
没有数字依据时，不宣称性能已提升。

## 29. 可观测性必须支持问题定位

**等级：SHOULD**

关键业务流程应有足够日志、指标或追踪信息，能够定位失败阶段、关联请求和识别资源异常。日志级别、采样和保留策略应合理，避免泄露敏感数据或造成过量开销。

**验收：** - 关键失败路径有日志； - 日志包含必要上下文和关联标识； -
敏感字段经过脱敏； - 日志不能替代错误处理和用户提示。

------------------------------------------------------------------------

# 第六部分：文档、注释与交付证据

## 30. 注释解释原因，不复述代码

**等级：SHOULD**

注释重点解释设计原因、业务约束、兼容要求、非直觉行为和已知陷阱。命名已经表达清楚的内容不应重复说明。

禁止无信息量的章节横幅、过时注释和无法验证的设计叙事。删除注释前应确认它是否记录了代码本身无法表达的约束。

**验收：** - 注释与当前实现一致； - 关键约束和非直觉行为有说明； -
不保留误导性或失效注释； - 不以注释数量作为质量指标。

## 31. 文档必须与实际行为一致

**等级：MUST（影响使用、部署、接口或维护的变更）**

README、配置示例、API
文档、架构说明、迁移说明和操作手册，应随相关实现变化同步更新。文档中的日期、版本、数字和支持范围必须有依据。

自动生成的提交列表不能直接冒充面向用户的发版说明。

**验收：** - 文档示例可运行或明确标注为示意； -
版本、参数和支持平台与实际一致； - 用户可见变更有清晰说明； -
未验证的能力不得写成已支持。

## 32. 验收证据必须随交付留档

**等级：MUST**

凡验收标准要求的测试输出、计数、日志、运行链接、截图、性能数据或设备验证记录，必须随交付物提供，或给出可访问的证据位置。

视觉变更应提供对应页面或状态的截图；构建通过不能替代视觉验收。

**验收：** - 证据与具体工作项一一对应； - 截图能识别版本、页面或场景； -
失败项和未验证项如实列出； - 证据可复查，不使用无法验证的口头结论。

------------------------------------------------------------------------

# 第七部分：变更、兼容与发布管理

## 33. 变更前必须评估影响范围

**等级：MUST**

修改前应识别受影响的模块、调用方、数据结构、配置、权限、用户流程、平台和外部系统。无法确定影响范围时，应先调查，不得直接假设"只影响当前文件"。

**验收：** - 列出直接影响与可能的间接影响； - 明确需要回归的场景； -
明确不在本次范围内的模块； - 高风险变更有回滚或恢复方案。

## 34. 身份、配置和存储变更必须显式决策

**等级：MUST**

包标识、应用名称、配置文件名、数据目录、凭据位置和持久化结构发生变化时，必须明确选择迁移、兼容读取或不迁移并告知用户影响。不得静默导致用户数据丢失或登录态失效。

**验收：** - 发布说明明确用户影响； -
迁移覆盖旧数据、新数据和新旧并存场景； - 迁移失败有恢复路径； -
不引入没有实际受益人的过度迁移机制。

## 35. 兼容契约与自有残留必须区分

**等级：MUST**

协议前缀、第三方互操作格式、外部服务识别标识和历史数据兼容字段，可能是功能契约，不得仅因命名过时就删除。自有品牌残留与外部兼容契约应分别列清单。

**验收：** - 清理前识别外部依赖方； - 保留清单和清理清单同时审查； -
兼容变更有回归测试； - 不以全仓字符串替换代替语义判断。

## 36. 功能债务与外观工作分开管理

**等级：SHOULD**

功能正确性、数据安全、稳定性和兼容性问题，应与命名统一、代码格式、视觉润色等外观工作分开记录、排期和汇报。外观工作可以有价值，但不得伪装成高优先级故障。

**验收：** - 每项工作标注类型和优先级； -
说明对用户或维护成本的实际影响； -
不让无关清理扩大高风险修复的变更范围。

## 37. 发布必须有版本、变更和恢复信息

**等级：SHOULD**

正式发布应明确版本号、用户可见变化、已知限制、兼容要求、数据迁移影响和必要的回滚/恢复方法。涉及不可逆数据变更时，应在发布前完成风险评估和备份策略。

**验收：** - 发布内容与实际构建产物一致； - 已知问题如实披露； -
用户升级路径明确； - 出现严重问题时有停止发布或恢复方案。

------------------------------------------------------------------------

# 第八部分：AI 编程智能体执行规范

## 38. 先理解项目，再修改代码

**等级：MUST**

AI
执行任务前，必须先检查项目结构、技术栈、入口、关键模块、现有规范、相关测试和工作区状态。不得仅根据用户描述或单个文件片段推断整个项目。

**验收：** - 说明已检查的关键文件和模块； - 确认当前分支及未提交变更； -
识别与任务相关的现有实现； - 信息不足时先调查或提出必要问题。

## 39. 修改前先给出执行计划与边界

**等级：MUST（中大型任务、重构、跨模块修改）**

开始实施前，应列出目标、根因判断、拟修改模块、预期行为变化、测试方案和范围外事项。小型且边界明确的单点修复可简化计划，但不能省略风险判断。

**验收：** - 计划与最终变更一致； - 新发现的范围变化先说明再执行； -
未获授权不擅自扩大任务； - 不覆盖用户已有的未提交修改。

## 40. 不得伪造执行结果或验证证据

**等级：MUST**

不得声称执行了实际未执行的命令、测试、构建、真机验证或发布。不得编造测试数量、截图、性能数据、运行链接或批准记录。

**验收：** - 报告中的命令和结果可追溯； - 未执行项明确标注； -
测试失败不得改写成通过； - 仅审查代码时不得声称功能已在真实环境验证。

## 41. 变更必须可审查、可回滚

**等级：MUST**

AI
应控制修改范围，避免无关格式化、批量重命名、依赖升级和文件搬迁。高风险操作前应确认备份、版本控制或恢复方式。

**验收：** - diff 只包含任务相关修改； -
未经要求不删除用户数据或配置； - 不覆盖未提交工作； -
重大变更有回滚说明。

## 42. 完成报告必须逐项对应验收标准

**等级：MUST**

AI
不得用"已完成""已优化""已修复"等概括性陈述代替证据。交付报告必须逐项说明改动、验证结果、证据等级、未完成事项和风险。

**验收：** - 每项要求都有对应结果； - 失败、跳过和未验证项单独列出； -
文件变更清单完整； - 不把计划完成当作实际完成。

# 第十部分：例外、验收与执行纪律

## 43. 规则冲突必须显式处理

**等级：MUST**

当通用规范、项目规范、用户明确要求、平台限制或外部接口契约发生冲突时，必须指出冲突内容及影响，不能静默选择对执行最方便的规则。

法律、安全、数据保护和平台强制要求不得被较低层级的项目约定覆盖。

## 44. 一项变更一项验收

**等级：SHOULD**

大型整改应拆成可独立审查和验证的工作项。高风险事项应逐项验收后再进入下一阶段，避免多个未经验证的变更叠加，使故障来源无法定位。

## 45. 完成以证据为准，不以自我声明为准

**等级：MUST**

执行方的"已完成""已批准""已验证"等声明，必须能对应到工作单中的验收标准和证据。没有证据的项目应标记为未验证，不得默认通过。

# 附录 A：一页速查

-   **根因优先**：禁止症状式补丁，不为形式重写而扩大范围。
-   **差异收敛**：环境差异集中管理，跨模块决策只有一个事实源。
-   **边界清楚**：核心业务与外部框架解耦，模块职责明确。
-   **数据可靠**：权威校验、安全写入、事务、并发控制和迁移版本化。
-   **安全默认**：凭据不入仓、最小权限、输入校验、防注入、隐私最少化。
-   **状态一致**：界面与外部真实状态对账，状态转换有定义。
-   **测试有效**：重构前建立基线，优先测试高风险和高变更频率路径。
-   **证据诚实**：审查、构建、自动化测试、真实环境和交付验收分级报告。
-   **变更可控**：先评估影响范围，保护兼容契约，重大变更有恢复方案。
-   **文档可信**：注释写原因，文档跟随实现，验收证据随交付留档。
-   **AI 受约束**：先理解项目，明确计划与边界，不伪造结果，不擅自扩围。
-   **验收闭环**：每项要求对应证据；没有证据，不算完成。

# 附录 B：项目启动时的适配清单

每个项目启动时，应至少明确：

1.  项目类型、目标用户和主要运行环境；
2.  技术栈、架构边界和模块责任；
3.  数据类型、数据存储位置、敏感级别和恢复要求；
4.  外部接口、第三方依赖和权限边界；
5.  测试命令、构建命令、CI 规则和真实环境验证方式；
6.  版本发布、迁移、回滚和用户支持方式；
7.  本规范中不适用或需要调整的条款及理由。

> **最终原则：工程质量不是代码看起来整洁，而是系统在预期和异常条件下都能保持正确；每一次变更都能被解释、验证、追溯，并在失败时得到控制。**
