# 现代软件工程与 AI Agent 研发治理体系 V1.0

**文档类型：** 通用工程治理标准\
**版本：** V1.0\
**适用范围：** 个人开发、小型项目、中型产品、大型研发组织及 AI
原生研发团队\
**规范属性：** 可裁剪、可配置、可审计的通用标准\
**核心原则：** 统一底线、分级治理、按需启用、证据驱动、人机协同

------------------------------------------------------------------------

## 1. 规范定位

### 1.1 建设目标

本体系用于规范软件从立项、需求分析、架构设计、编码实现、测试验证、发布交付到运行维护的全过程，并明确
AI Agent 在研发活动中的身份、权限、执行边界、协作方式和监督机制。

本体系不是要求所有项目采用同一套繁重流程，而是提供统一的工程底线与治理框架。项目根据规模、复杂度、业务影响和风险等级，选择适用的治理配置。

### 1.2 适用项目

本体系可用于但不限于：

-   脚本、命令行工具、自动化任务和个人项目。
-   网站、桌面应用、移动应用和独立软件产品。
-   SaaS、企业应用、业务中台和内部平台。
-   微服务、分布式系统、数据平台和云原生系统。
-   使用单 Agent、多 Agent 或人机混合方式开展研发的项目。
-   金融、医疗、工业、政务等需要专项治理的高风险系统。

### 1.3 不替代的规范

本体系提供通用治理框架，不替代适用法律法规、合同要求、行业监管要求、组织安全政策和项目专项技术标准。发生冲突时，按第
5 章的优先级规则处理。

------------------------------------------------------------------------

## 2. 基本原则

1.  **风险匹配：** 治理强度与项目风险、复杂度和影响范围相匹配。
2.  **统一底线：**
    项目可以简化流程，但不得绕过安全、数据保护、真实性和可追溯性底线。
3.  **最小必要：**
    只引入能够降低实际风险或提升交付质量的流程、文档和审批。
4.  **单一事实源：**
    需求、接口、配置、数据结构和系统状态应有明确权威来源。
5.  **证据驱动：** 结论应区分已验证、部分验证、推断和未验证。
6.  **可追溯：** 重要需求、决策、变更、测试、发布和事故应能追踪。
7.  **人类负责：** AI Agent
    可以承担任务，但业务责任、风险接受和授权审批必须由明确的人类责任主体承担。
8.  **可恢复：**
    对重要数据和关键服务，应设计备份、回滚、恢复或降级路径。
9.  **持续改进：** 规范应根据缺陷、事故、交付数据和技术变化定期修订。
10. **工具不等于治理：** 仅有 Markdown
    规则或提示词不构成强制控制；关键规则应通过权限、沙箱、CI、审批和审计机制落实。

## 3. 术语与规范等级

### 3.1 术语

-   **项目：** 为交付软件、系统、服务或技术成果而开展的一组活动。
-   **治理配置（Project Governance Profile）：**
    针对单个项目选定的治理等级、适用规则、审批要求和验证要求。
-   **Agent：** 能够依据目标调用模型、工具或外部系统执行任务的软件代理。
-   **编排器（Orchestrator）：**
    负责拆解任务、分派工作、协调依赖和汇总结果的 Agent 或控制程序。
-   **人工责任人：** 对项目结果、风险接受或关键操作承担明确责任的人。
-   **独立审查：**
    由未直接完成被审查工作的人或独立自动化机制进行的检查。
-   **证据：**
    能够支持某项结论的测试结果、日志、代码审查记录、构建产物、审批记录或运行数据。

### 3.2 规范等级

  等级         含义       使用要求
  ------------ ---------- --------------------------
  MUST         强制要求   所有适用项目必须满足
  MUST NOT     强制禁止   所有适用项目不得违反
  SHOULD       强烈建议   不执行时应说明理由及风险
  SHOULD NOT   不建议     确有必要时应说明理由
  MAY          可选要求   按项目需要启用

"适用项目"指根据项目治理配置和风险评估被判定需要执行该规则的项目。不得通过降低项目等级规避法律、监管、合同或组织强制要求。

## 4. 项目分级与治理强度

### 4.1 项目等级

  等级        典型范围                                       治理方式
  ----------- ---------------------------------------------- ----------
  P0 微型     一次性脚本、简单自动化、短期验证               极简治理
  P1 小型     个人应用、小型网站、内部轻量工具               轻量治理
  P2 中型     正式桌面/移动应用、SaaS、持续维护产品          标准治理
  P3 大型     多团队系统、复杂业务平台、分布式系统           完整治理
  P4 关键型   高业务影响、高监管、高安全或生命财产相关系统   强化治理

项目等级不是只按代码量、人数或预算确定。应综合考虑：

-   用户规模和影响范围。
-   数据敏感程度与数据丢失后果。
-   安全、财务、法律和声誉影响。
-   系统复杂度、依赖数量和集成边界。
-   可用性、实时性和恢复目标。
-   变更频率、团队数量和供应链风险。
-   AI Agent 获得的工具权限及其可造成的影响。

### 4.2 风险优先于规模

小项目若处理敏感数据、资金、身份认证或生产环境，也可能需要 P3/P4
级别的专项控制。大型项目中的低风险实验模块可以在隔离环境中采用较轻流程，但不得影响系统级强制控制。

### 4.3 治理配置原则

每个持续维护的项目 SHOULD 建立治理配置文件。P0 一次性任务 MAY
使用简短工作单代替完整配置。

治理配置至少明确：

-   项目等级及风险等级。
-   项目负责人和技术负责人。
-   适用规范及其版本。
-   必须执行的测试和审查。
-   Agent 可用工具、数据和环境范围。
-   高风险操作的人工审批要求。
-   发布、回滚和数据恢复要求。
-   例外项、责任人和到期时间。

## 5. 标准体系与冲突处理

### 5.1 标准分层

本体系由以下标准组成：

1.  **治理总纲：** 定义原则、适用范围、等级、责任和冲突处理。
2.  **通用软件工程规范：** 约束架构、编码、数据、测试、发布和维护质量。
3.  **AI Agent 研发治理规范：** 约束 Agent
    的任务、权限、执行、协作、验证和审计。
4.  **团队与项目管理规范：**
    约束组织职责、需求优先级、资源、进度、跨团队协作和交付。
5.  **专项工程规范：** 针对行业、技术栈、平台、安全或合规要求进行扩展。
6.  **项目治理配置：** 将上述规则映射为当前项目实际执行要求。

### 5.2 冲突优先级

发生要求冲突时，按以下顺序处理：

1.  适用法律法规及监管要求。
2.  合同、客户和行业强制要求。
3.  组织级安全、隐私、合规和风险政策。
4.  项目专项强制标准。
5.  本体系及其通用工程规范。
6.  项目局部约定和个人偏好。

低优先级规则不得削弱高优先级规则。无法确定优先级时，应暂停相关高风险操作并提交责任人裁定。

### 5.3 例外管理

例外必须记录：规则编号、原因、影响范围、风险评估、补偿控制、批准人、开始时间和到期时间。例外不得永久默认为规则废止。到期后必须复审、续期或关闭。

## 6. 组织职责与责任边界

### 6.1 基本职责

  角色                  主要责任
  --------------------- --------------------------------------------
  业务/产品负责人       目标、需求优先级、业务验收和业务风险接受
  项目负责人            计划、资源、依赖、进度、风险和交付协调
  技术负责人/架构师     技术方案、架构约束、技术风险和技术决策
  开发人员              代码实现、自测、变更说明和缺陷修复
  测试/质量负责人       测试策略、质量证据、缺陷风险和验收建议
  安全/隐私负责人       安全与隐私评估、专项控制和风险建议
  发布/运维负责人       环境、发布、监控、回滚和运行维护
  Agent 负责人/操作者   Agent 配置、授权、监督、结果核验和操作追责

小项目允许一人承担多个角色，但关键风险决策应避免由同一执行主体未经复核自行批准。

### 6.2 人类责任边界

-   MUST
    为生产发布、数据删除、权限提升、资金操作等高影响行为指定人类责任人。
-   MUST 明确谁有权批准风险接受和例外。
-   MUST 对 Agent 的执行范围和授权方式负责。
-   MUST NOT 将"模型建议""Agent 已执行"视为责任转移。
-   SHOULD 对高风险变更实施执行与批准分离。

## 7. 软件工程生命周期治理

### 7.1 生命周期

标准生命周期如下：

1.  需求提出与准入。
2.  范围、目标和验收标准确认。
3.  风险分级与治理配置。
4.  技术方案与架构决策。
5.  任务拆分与工作分配。
6.  编码、配置和数据变更。
7.  测试、审查和安全验证。
8.  发布评估与部署。
9.  运行监控、反馈和维护。
10. 退役、迁移和数据处置。

P0/P1 项目可以合并阶段和文档，但不得省略目标确认、必要验证和安全边界。

### 7.2 需求管理

每项重要需求 SHOULD 明确：

-   背景与目标。
-   用户或业务价值。
-   范围内事项与明确不做事项。
-   功能和非功能要求。
-   验收条件。
-   依赖、假设和限制。
-   风险与数据影响。
-   优先级和责任人。

需求变化 MUST 评估对范围、架构、数据、测试、计划和兼容性的影响。

### 7.3 架构与技术决策

-   P2 及以上项目 SHOULD 记录重要架构决策。
-   P3/P4 项目 SHOULD 设置架构评审或等效机制。
-   关键决策应记录背景、候选方案、取舍、后果和复审条件。
-   架构应明确模块边界、数据所有权、接口契约和故障边界。
-   SHOULD 避免无明确收益的过度抽象和不必要的分布式复杂度。

### 7.4 编码与代码审查

-   代码 MUST 遵循项目约定的格式、命名、错误处理和目录结构。
-   变更 MUST 尽量聚焦单一目的，避免混入无关重构。
-   重要逻辑 MUST 有可验证的测试或等效证据。
-   P2 及以上项目 SHOULD 对关键变更实施代码审查。
-   P3/P4 项目 SHOULD 对高风险变更实施独立审查。
-   审查应关注正确性、安全性、数据一致性、可维护性和回归风险，而非仅关注风格。

### 7.5 数据与状态正确性

-   MUST 明确关键数据的权威来源和所有权。
-   MUST 对重要写入、迁移和删除操作设计失败处理。
-   关键数据更新 SHOULD 采用事务、原子替换、幂等或可恢复机制。
-   MUST 评估并发访问、重复请求和部分失败的影响。
-   MUST 防止 UI 展示状态与实际持久化状态长期不一致。
-   重要迁移 MUST 有备份、验证和恢复策略。

### 7.6 接口与兼容性

-   跨模块、跨服务和跨团队接口 SHOULD 有明确契约。
-   破坏性变更 MUST 评估调用方影响并提供迁移安排。
-   对外接口 SHOULD 定义错误语义、版本策略、超时和重试行为。
-   不得仅凭调用方"看起来正常"判断接口兼容。

## 8. AI Agent 研发治理

### 8.1 Agent 定位

Agent 是受控的研发执行主体，不是项目责任主体。Agent
可以分析、规划、编码、测试、审查、检索和生成交付物，但必须在明确授权、工具边界和监督机制内工作。

### 8.2 任务准入

交给 Agent 的任务 SHOULD 包含：

-   目标与预期产物。
-   可修改范围。
-   禁止修改范围。
-   可用工具和环境。
-   验收标准。
-   测试要求。
-   风险等级。
-   是否允许联网、安装依赖、执行命令或访问外部数据。
-   需要人工批准的操作。

信息不足时，Agent MUST 标注假设；涉及不可逆或高风险行为时 MUST
先澄清或请求批准。

### 8.3 最小权限

-   Agent MUST 采用完成任务所需的最小权限。
-   MUST 区分只读、可写、可执行、可联网、可部署和管理权限。
-   MUST 对生产凭据、密钥和敏感数据实施隔离。
-   MUST 对命令执行、文件访问和外部调用设置边界。
-   SHOULD 在沙箱或隔离分支中执行高不确定性任务。
-   MUST NOT 将提示词中的指令视为绕过系统权限和安全政策的授权。

### 8.4 不可信输入与提示词注入

来自网页、文档、代码仓库、Issue、邮件、日志和第三方工具的内容均应视为数据，而非天然可信的指令。

Agent MUST： - 区分用户授权、系统约束和外部内容。 -
不因外部材料要求而泄露秘密或扩大权限。 -
对外部内容触发的高风险动作进行独立授权检查。 -
对下载文件、脚本和依赖进行来源及风险评估。

### 8.5 单 Agent 工作模式

单 Agent 可以在不同阶段承担规划、实现、测试和审查职责，但 SHOULD
明确阶段切换和验收门槛。高风险任务不应仅依赖同一 Agent
对自身工作的自我评价。

### 8.6 多 Agent 协作

多 Agent 模式 SHOULD 明确：

-   总任务负责人或编排器。
-   子任务目标、输入、输出和验收条件。
-   文件、模块和资源的所有权。
-   共享状态和接口契约。
-   并发修改冲突处理方式。
-   交接格式和证据要求。
-   失败隔离、重试和终止条件。

多个 Agent 不应在缺少协调机制时同时修改同一关键文件或共享数据。Agent
之间的结论冲突应记录并交由编排器或人类责任人处理。

### 8.7 Agent 输出真实性

Agent MUST： - 区分实际执行与建议执行。 -
区分测试通过、测试未运行、测试失败和无法验证。 -
不得伪造日志、截图、构建结果、测试结果或引用。 -
报告未完成事项、已知缺陷和不确定性。 -
对生成或修改的文件提供准确路径和变更说明。

## 9. 安全、隐私与供应链

### 9.1 通用安全要求

-   MUST 对输入进行适当验证和规范化。
-   MUST 对身份认证、授权和敏感操作实施访问控制。
-   MUST 防止秘密进入代码仓库、日志、提示词和交付物。
-   MUST 对外部依赖和构建工具保持基本来源管理。
-   MUST 根据风险处理漏洞、依赖更新和安全告警。
-   SHOULD 对关键操作保留审计记录。

### 9.2 隐私与数据治理

-   MUST 识别项目处理的数据类型及其敏感程度。
-   MUST 遵循数据最小化原则。
-   MUST 明确数据收集、使用、共享、保存和删除规则。
-   MUST 在向模型或第三方服务发送数据前评估授权与隐私风险。
-   MUST 对测试数据进行脱敏或使用合成数据，除非已获得合规授权。
-   MUST 对数据导出、删除和共享设置相应权限。

### 9.3 供应链

P2 及以上项目 SHOULD 管理依赖清单、版本锁定和来源信息。P3/P4 项目 SHOULD
建立依赖漏洞响应、构建来源验证和发布产物完整性检查。

------------------------------------------------------------------------

## 10. 测试、验证与质量门禁

### 10.1 测试策略

测试强度应与风险相匹配，可包括：

-   静态检查、格式检查和类型检查。
-   单元测试。
-   集成测试。
-   端到端测试。
-   安全测试。
-   性能与容量测试。
-   兼容性与迁移测试。
-   恢复、回滚和故障演练。

### 10.2 验证证据等级

  等级   证据                     可支持的结论
  ------ ------------------------ --------------------------
  V0     仅阅读或推理             未执行验证
  V1     静态检查或局部检查       局部结构或规则符合
  V2     单元测试或局部自动测试   局部行为通过
  V3     集成/端到端测试          指定集成路径通过
  V4     目标环境验证             指定目标环境下通过
  V5     生产监控或真实运行证据   指定时间和范围内运行正常

不得将低等级证据描述为高等级验证。测试范围、环境、数据和时间应清楚记录。

### 10.3 质量门禁

-   P0/P1：至少执行与变更风险相称的检查和基本自测。
-   P2： SHOULD 建立自动化测试和合并前检查。
-   P3： SHOULD 建立 CI 门禁、审查和发布验收。
-   P4： MUST 根据适用法规、合同和安全要求建立独立验证与审批。

质量门禁失败时，不得通过修改报告文字将失败伪装为通过。确需带风险交付时，必须走例外审批流程。

------------------------------------------------------------------------

## 11. 发布、运行与恢复

### 11.1 发布管理

发布前 SHOULD 确认：

-   变更范围和版本信息。
-   测试与审查证据。
-   配置和数据库迁移。
-   兼容性和依赖影响。
-   监控、告警和回滚方案。
-   发布责任人及审批要求。

P3/P4 项目 SHOULD 采用分批、灰度或其他风险可控的发布策略。

### 11.2 运行维护

持续运行的系统 SHOULD
明确服务责任人、日志、监控、告警、备份和故障处理流程。关键系统应定义可用性目标、恢复时间目标（RTO）和恢复点目标（RPO）。

### 11.3 事故处理

发生安全、数据、可用性或重大质量事故时，应：

1.  控制影响并保护人员、数据和系统。
2.  按预定机制通知责任人。
3.  保留必要证据和审计记录。
4.  评估是否需要回滚、隔离或恢复。
5.  分析根因和系统性诱因。
6.  制定纠正与预防措施。
7.  更新测试、监控、规范或培训。

------------------------------------------------------------------------

## 12. 团队与项目管理

本章主要面向 P2 及以上项目；P0/P1 可采用简化方式。

### 12.1 计划与优先级

-   明确目标、范围、里程碑和交付责任。
-   需求优先级应考虑价值、成本、风险和依赖。
-   计划应显式包含测试、集成、修复和发布工作。
-   进度报告应反映真实状态，不以任务关闭数量替代实际交付价值。

### 12.2 跨团队协作

-   明确跨团队接口、负责人和交付时间。
-   对关键依赖设置风险缓冲和升级路径。
-   重要交接应包含背景、当前状态、未决问题和验收证据。
-   共享组件和平台应有明确维护责任。

### 12.3 知识管理

重要系统应维护足以支持开发、排障和交接的文档。文档应标明适用版本或更新时间，过期内容应及时修订或标记。

### 12.4 资源与成本

P2 及以上项目 SHOULD
关注人力、云资源、模型调用、第三方服务、构建和测试成本。成本优化不得以破坏安全、可靠性或数据正确性为代价。

------------------------------------------------------------------------

## 13. 可观测性与持续改进

项目可根据自身特点选取指标，不应为了指标而制造无意义工作量。

建议指标包括：

-   需求交付周期。
-   变更失败率。
-   缺陷逃逸率。
-   生产事故数量与恢复时间。
-   自动化测试覆盖的关键路径。
-   发布频率与回滚率。
-   安全问题修复时长。
-   Agent 任务一次验收通过率。
-   Agent 产生的返工率。
-   Agent 越权尝试和策略拦截次数。
-   人工审批等待时间。
-   文档与实际实现的一致性。

指标必须结合上下文解释，不得单独用代码行数、提交次数、Agent
调用次数或测试覆盖率评价个人或团队真实生产力。

------------------------------------------------------------------------

## 16. 规范落地路线

### 阶段一：建立底线

发布核心规则、项目等级、责任边界和最小验证要求。先确保项目知道什么绝对不能做。

### 阶段二：项目配置化

为不同项目建立治理配置，明确哪些规则适用、哪些流程可以简化。

### 阶段三：工具化执行

将规则映射到实际工具：代码仓库权限、分支保护、CI、测试、沙箱、Agent
工具白名单、审批和审计日志。

### 阶段四：质量度量

收集真实缺陷、事故、返工、交付和 Agent 执行数据，验证治理机制是否有效。

### 阶段五：持续优化

定期复审规则，删除无效流程，补充事故暴露的缺口，并维护规范版本和兼容策略。

## 17. 成熟度模型

  等级          状态       特征
  ------------- ---------- ---------------------------------
  M0 无治理     临时执行   规则依赖个人经验
  M1 有规范     文档化     有标准，但主要靠自觉
  M2 可配置     分级执行   项目按规模和风险选择规则
  M3 可验证     自动检查   关键规则接入测试、CI 和权限机制
  M4 可审计     全程留痕   决策、执行、审批和交付可追踪
  M5 持续优化   数据驱动   根据风险和效果持续调整治理体系

成熟度不等于项目等级。小项目可以在适用范围内达到较高治理成熟度，大项目也可能因执行不到位而处于低成熟度。

## 19. 版本维护

-   本规范 SHOULD
    至少每年复审一次；发生重大安全事故、重大技术变化或治理模式变化时应提前复审。
-   规范修订应记录版本、变更内容、兼容性影响和生效日期。
-   项目应记录实际采用的规范版本。
-   新版本不得在未说明的情况下追溯改变既有项目的验收约定。
-   组织可发布行业附录、技术栈附录和项目模板，但不得降低适用的强制底线。

## 20. 核心结论

本体系采用"统一底线、分级治理、按需启用、证据驱动、人机协同"的方式，支持从个人脚本到大型关键系统的不同工程场景。

**小项目不必承担大型项目的全部管理成本；大型项目不能缺少与其风险相匹配的控制；AI
Agent 无论单独工作还是多 Agent
协作，都必须处于明确授权、可验证、可追溯和有人负责的工程体系之内。**

规范本身只是治理基线。只有当适用规则被落实到团队职责、项目配置、权限系统、开发工具、自动化测试、审批和审计机制中时，治理体系才真正生效。
