# 质量门禁

## 最小门禁

任何代码变更均需：范围与任务一致；保护用户已有修改；执行与变更相关的验证（无法执行时说明）；检查实际 Diff；报告未完成项和风险。

## 五条工程底线核对

逐条判断是否涉及本次变更：
1. 禁补丁：变更落在源头完整逻辑单元，不叠加症状特判或留下两套可达逻辑。
2. 单一事实源：跨模块决策只有一个权威计算/定义来源。
3. 权威哈希：下载、导入、复用跳过逻辑在上游提供哈希时执行校验。
4. 原子写：涉及用户状态文件写入时按规范使用原子写路径。
5. 界面对账：涉及外部状态镜像时验证刷新、失效项处理和操作前校验。

不涉及项标注 N/A＋理由；适用项不满足时不得宣称通过。细则以 `references/软件工程规范-通用复用版-增强版.md` 原文为准。

## 按风险增强

- R0/R1：相关测试/运行验证、Diff 检查。
- R2：影响分析、单元/集成/回归测试、兼容性检查、恢复说明。
- R3：明确授权、备份/恢复验证（适用时）、分阶段执行、数据一致性与安全检查、停止条件。

## 证据等级

- E0：未验证。
- E1：静态检查/代码审查。
- E2：局部命令或单元测试。
- E3：集成测试/构建/启动验证。
- E4：端到端或关键业务流程验证。
- E5：生产观测、灰度或恢复验证（仅适用且获授权时）。

不得为了追求更高等级执行无必要或有风险的测试。结论必须标注实际达到的等级和覆盖范围。

## 专项门禁

- 项目骨架：仅新项目或经确认的重大骨架变化执行。
- 桌面三端：仅 Windows/macOS/Linux 桌面多端产品执行。
- UI：仅 UI 任务执行；构建通过不能替代视觉和交互验收。

不适用项说明原因，不得伪装成已执行。
