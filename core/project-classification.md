# 项目状态识别与工作流路由

## 1. 先分清两个维度

- **项目生命周期状态**：新建、原型、活跃、维护、退役。
- **本次任务模式**：NEW_PROJECT / PROJECT_TAKEOVER / SECONDARY_DEVELOPMENT / REFACTORING / MAINTENANCE / MIGRATION。

项目正在维护，不代表每个任务都是 MAINTENANCE；一个活跃项目也可能执行 MIGRATION。

## 2. 六种模式边界

| 模式 | 进入条件 | 不负责 | 退出条件 |
|---|---|---|---|
| NEW_PROJECT | 从需求开始建立新项目 | 未确认需求的功能堆叠 | 最小工程骨架可运行、核心规则和验证方式落档 |
| PROJECT_TAKEOVER | 现有项目需要摸清现状 | 未授权改业务代码、自动重构 | 项目画像、Git/运行基线、风险和未知项交付 |
| SECONDARY_DEVELOPMENT | 新增功能或改变业务行为 | 顺手整理无关技术债 | 新行为按验收条件实现，兼容和回归检查完成 |
| REFACTORING | 内部结构改善，外部行为保持 | 偷渡业务需求变化 | 行为基线保持，结构目标有证据，回归完成 |
| MAINTENANCE | Bug、故障、稳定性或常规维护 | 借修复之名做大规模架构重写 | 根因/修复有说明，回归验证和残余风险明确 |
| MIGRATION | 技术栈、数据、平台、运行环境改变 | 未授权生产切换或删除旧数据 | 迁移目标、数据/行为校验、切换与回滚条件完成 |

## 3. 组合与切换

- 接管 → 二开：先完成只读基线，再针对具体需求进入二开。
- 接管 → 重构：先评估，再确认重构目标和行为基线。
- 维护 → 重构：若根因是结构性缺陷且修复必须改变结构，先解释，再拆分根因修复/重构阶段。
- 二开 → 重构：若新增功能前必须先整理结构，单独定义前置重构验收，不把两种验收混为一谈。
- 迁移可包含二开、重构和维护子阶段；迁移总计划仍作为主工作流。

切换模式时保留前一阶段证据，不重新造一份项目基线。

## 4. 选择规则

1. 用户明确说“先接手/先了解/先评估”，主模式为 TAKEOVER，即使后续目标可能是二开。
2. 用户要求改变功能或业务行为，主模式为 SECONDARY_DEVELOPMENT。
3. 用户要求不改变外部行为、只调整内部结构，主模式为 REFACTORING。
4. 用户描述故障或缺陷，主模式为 MAINTENANCE。
5. 用户要求更换平台/技术栈/数据库/运行环境，主模式为 MIGRATION。
6. 全新空目录或从需求开始，主模式为 NEW_PROJECT。
7. 目标不清楚时只问一个最关键问题；可先做安全的只读发现时，不用长问卷阻塞。
