# 规范识别与调度

YoYo 是唯一入口。参考规范是规则来源，不要求用户另行安装或调用其他 Skill。

## 1. 规范职责与权威边界

| 规范 | 职责 | 触发条件 | 加载方式 |
|---|---|---|---|
| `软件工程规范-通用复用版-增强版.md` | 通用代码、架构、依赖、数据、安全、测试和维护要求 | 所有涉及工程实现的任务 | 按本次变更涉及的章节查阅 |
| `项目实施与持续验收规范-通用复用版-V1.0.md` | 任务边界、计划、阶段实施、质量门禁、证据、交付与恢复 | 所有实质性工程任务 | 按当前阶段读取，不把它当作技术条款替代物 |
| `项目启动规范.md` | 项目骨架、分层、模块职责、目录、文件角色和质量护栏 | 新项目；存量项目重大架构/骨架变化 | 新项目业务代码前完成适用项；存量项目先基线，再决定目标结构 |
| `三端规范-通用复用版-V1.1-修订稿.md` | Windows/macOS/Linux 桌面多端平台抽象、数据/配置、构建发布和跨端验收 | 同一桌面产品目标平台包含 Windows/macOS/Linux 中至少两个 | 仅读取适用平台条款；不适用于 Web+移动端等其他组合 |
| `UI 设计质量与反模板化规范.md` | UI 审计、设计方向、视觉/交互实现与 UI 验收 | 新增/修改页面、组件视觉、布局、样式、交互、界面文案或 UI 审查 | 按 UI 任务范围读取；非 UI 后端任务不加载 |

## 2. 组合规则

| 任务 | 加载规范 |
|---|---|
| 新建纯后端/API/CLI | 软件工程增强版 + 持续验收规范 + 项目启动规范 |
| 新建 Web/前端项目 | 上述三份 + UI 规范 |
| 新建桌面跨端项目 | 上述三份 + 三端规范；涉及界面时加 UI 规范 |
| 接管，只读评估 | 持续验收规范 + 软件工程规范；项目启动规范只用于评估骨架现状 |
| 普通二次开发 | 持续验收规范 + 软件工程规范；触及骨架时加项目启动规范；触及 UI/桌面多端时追加对应规范 |
| 重构 | 持续验收规范 + 软件工程规范；涉及骨架、UI 或桌面跨端时追加对应规范 |
| Bug/日常维护 | 持续验收规范 + 软件工程规范；触及 UI/桌面跨端时追加对应规范 |
| 技术/数据/平台迁移 | 持续验收规范 + 软件工程规范；按目标结构、平台和 UI 变化追加专项规范 |

## 3. 冲突处理

1. 先确认两条规则是否作用于同一对象、同一阶段和同一适用条件。
2. 不得把不同规范的规则等级互相转换；MUST/SHOULD/MAY 以原文为准。
3. 同一领域内更具体、更可验的条款用于解释通用条款，但不能静默削弱另一条明确 MUST。
4. 若两条适用的 MUST 无法同时满足，列出规范名称、条款、冲突点和影响，暂停冲突部分并交用户裁定。
5. 安全、数据正确性和用户权益底线不得被视觉、平台便利或进度要求覆盖。

## 4. 适用记录

在 `.yoyo/PROJECT_PROFILE.yaml` 的 `governance.specifications` 中记录已采纳、部分采纳或 N/A 的规范及原因。已有等价记录时更新，不重复创建。不得把“未读取”写成“N/A”；N/A 必须有适用性理由。

## 5. 不再作为运行时规范加载的旧资料

V1.5 不再把以下旧版/宽泛治理文档并列为运行时规范，以免与当前选定的通用工程增强版和过程验收规范形成多套权威：`通用软件工程规范_V2.0.md`、`AI Agent 通用工程治理规范 V1.0.md`、`现代软件工程与 AI Agent 研发治理体系 V1.0.md`。这不代表这些资料被判定为错误；其内容若已被选定规范吸收，则以当前规范为准。若用户明确要求审查这些旧资料，可作为历史/补充材料单独读取，不自动改变规范优先级。
